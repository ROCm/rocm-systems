.. _what-is-cuid:

**************
What is CUID?
**************

The Component Unified Identifier (CUID) is a unique value generated by combining device-specific data into a 122-bit ID value and displayed to the user in a UUIDv8 style format. This can either be a primary CUID or a derived CUID. The CUID library implements the necessary logic and functions to generate both types of CUIDs.

Primary CUID
=============

The following table shows the corresponding bits for device-specific data, which are further used to generate a primary CUID:

.. list-table:: Device-specific data in bits
   :widths: 20 40 60
   :header-rows: 1

   * - Bits
     - Device-specific data
     - Details

   * - 0:63
     - Device serial number/Fingerprint
     - This serial number can be available as any of the following:

       * PCIe configuration DSN caps (endpoint).

       * SMBIOS platform serial number.

       * ACPI or other architectural component identifier. If ACPI is unavailable, a software-generated fingerprint from proprietary individual marker is used.

       This serial number can be MSB 0-extended if smaller than 64 bits or truncated if larger.

   * - 64:71
     - UnitID (part 1)
     - Used if the component supports a unit ID; otherwise, this value is 0.

   * - 72:79
     - RevisionID
     - Used if the component supports revision ID; otherwise, this value is 0.

   * - 80:95
     - DeviceID
     - The device ID can be available as any of the following:

       * Present in the PCIe configuration space.

       * Present in the SMBIOS ID.

       * For CPU: Family number and Model number values combined.

   * - 96:111
     - VendorID
     - The vendor ID can be available as any of the following:

       * Present in the PCIe configuration space.

       * SMBIOS vendor ID.

       The vendor ID follows the PCIe vendor ID 16-bit value definition, such as 0x1022 or 0x1002 for AMD.

   * - 112:116
     - UnitID (part 2)
     - Used only if the UnitID value is >= 256; otherwise, this value is considered 0. UnitID is therefore 13 bits in total, split across bits 64:71 and 112:116.

   * - 117
     - Temporary marker
     - 0 in every primary CUID. Only a temporary CUID has it set; see :ref:`temporary-cuid`. This bit is not part of UnitID, which is why UnitID part 2 ends at bit 116.

   * - 118:121
     - Component Type
     - Present as ``amdcuid_device_type_t`` in ``amd_cuid.h``, which uses the on-wire values directly.

The Component Type field uses the following values:

.. list-table:: Component Type values
   :widths: 20 40
   :header-rows: 1

   * - Value
     - Type

   * - 0x0
     - Platform

   * - 0x1
     - CPU

   * - 0x2
     - GPU

   * - 0x3
     - NIC

   * - 0x4
     - NPU

   * - 0x5
     - Storage

   * - 0x6
     - Memory

   * - 0x7
     - Generic PCIe device

   * - 0x8
     - Generic component

   * - 0x9
     - Rack tray

   * - 0xA
     - Rack

   * - 0xB - 0xE
     - Reserved

   * - 0xF
     - Other

The field spans an octet boundary: its low two bits are the top two bits of payload octet 14, and its high two bits are the low two bits of payload octet 15. A producer that drops payload bits 120:121 renders the type modulo 4, which makes an NPU collide with a Platform.

The values present in the corresponding bit positions (first column in the preceding table) are also used to fill out a UUIDv8 style format to generate the primary CUID as shown in the following table:

.. list-table:: UUIDv8 style format
  :widths: 20 40 40
  :header-rows: 1

  * - Bit position
    - Value
    - Note

  * - 0:47
    - ID value (part 1)
    - LSB of ID value.

  * - 48:51
    - A fixed value of 8
    - The value is fixed for `RFC 9562 <https://www.rfc-editor.org/rfc/rfc9562.html>`_ compliance.

  * - 52:63
    - ID value (part 2)
    -

  * - 64:65
    - A fixed value of 10b
    - The value is fixed for `RFC 9562 <https://www.rfc-editor.org/rfc/rfc9562.html>`_ compliance.

  * - 66:127
    - ID value (part 3)
    - MSB of ID value.

The version and variant bits are inserted rather than overwritten: they displace the payload after them instead of replacing payload content. The framing therefore preserves every one of payload bits 0 through 121 and discards exactly payload bits 122 through 127, which are always zero, so the payload can be recovered from the rendered UUID exactly.

Because the bit positions above are numbered MSB-first over the rendered octets, the least significant payload octet appears at the front of the printed UUID string. For example, the payload ``1032547698badcfe0000a37302108000`` renders as ``10325476-98ba-8dcf-b800-028dcc084200``.

Because the device serial number is protected information, the primary CUID generated from it is also protected at the same level. Users with the right privilege can consider the primary CUID as the direct link between the device and its derived CUID.

Derived CUID
=============

For typical day-to-day operations, the derived CUID is used. It is derived by hashing the primary CUID using HMAC-SHA2-256 (keyed hash) using a 256-bit key. The derived CUID obscures hardware details from lower-privilege software and prevents precomputed table attacks.

The key is the node key, a 256-bit HMAC key as described in FIPS 198-1, The Keyed-Hash Message Authentication Code (HMAC). Anyone holding the key can confirm a guessed serial number, so it must be random, unique per deployment, and readable only by root. This version of the library holds no node key and reads no CUID from a driver, so every CUID it returns is a temporary CUID; see :ref:`temporary-cuid`.

If the node key changes, every derived CUID computed with it changes. Primary CUIDs do not change, so they still trace each derived CUID back to its device.

The key is the HMAC key and the 16 packed primary payload octets are the HMAC message. The 256-bit digest is folded into the derived payload as follows:

.. list-table:: Derived CUID payload
   :widths: 20 60
   :header-rows: 1

   * - Bits
     - Content

   * - 0:63
     - Digest bits 0:63.

   * - 64:71
     - Reserved, zero. The UnitID slot is left empty so that the derived CUID can mask the sub-unit distinction where it is not wanted.

   * - 72:116
     - Digest bits 64:108, that is 45 bits.

   * - 117
     - Temporary marker, 0.

   * - 118:121
     - Reserved, zero.

The derived payload is then rendered as a UUIDv8 by the same rule as the primary. The digest slot is 45 bits rather than 46 because bit 117 is the temporary marker in both layouts.

.. _temporary-cuid:

Temporary CUIDs
================

A temporary CUID names a component without a node key, a driver or a serial number: every input is readable by any user. It is not derived from a primary CUID, and there is no temporary primary CUID; a request for one fails with ``AMDCUID_STATUS_UNSUPPORTED``.

The library packs a 32-octet structure ``S`` for the component and computes ``HMAC-SHA256(key = S, message = the 16 octets of the CUID application ID deeda863-4023-5bac-865a-9923e61370d7)``. It keeps the first 16 octets of the digest, sets the UUID version to ``8`` and the variant to ``10b``, and sets payload bit 117, which is the most significant bit of the last UUID octet. The other 121 bits are hash output. A CUID is temporary if and only if it is a UUIDv8 with that bit set; in the printed string the second-to-last hex digit is ``8`` to ``f``. amd-smi reports such a CUID with ``auxiliary`` set (``AUXILIARY: True``).

.. list-table:: Temporary structure S, packed least significant bit first
   :widths: 20 30 60
   :header-rows: 1

   * - Bits
     - Field
     - PCIe function, CPU package, platform

   * - 0:15
     - Format
     - 1 for a PCIe function, 2 for a CPU package or the platform.

   * - 16:143
     - Machine ID
     - The 16 octets of the machine-id, in file order.

   * - 144:175
     - Routing ID
     - ``((segment & 0xFFFF) << 16) | (bus << 8) | (device << 3) | function``; for a CPU its physical package ID; 0 for the platform.

   * - 176:183
     - RevisionID
     - PCI revision; CPUID stepping; 0.

   * - 184:199
     - DeviceID
     - PCI device ID; ``(family << 8) | model`` from CPUID; 0.

   * - 200:215
     - VendorID
     - PCI vendor ID; ``0x1022`` (AMD) or ``0x8086`` (Intel); 0.

   * - 216:219
     - Component Type
     - The component's type; 1 for a CPU; 0 for the platform.

   * - 220:223
     - Reserved
     - 0.

   * - 224:239
     - UnitID
     - See :ref:`cuid-gpu-partitions`; a NIC's PCI function number; 0 otherwise.

   * - 240:255
     - Segment high
     - ``segment >> 16`` for a PCIe function, so a VMD domain such as ``10000`` stays apart from domain ``0000``; 0 otherwise.

There is one temporary CUID per CPU package, per PCIe function and for the platform. A CPU whose vendor is neither ``AuthenticAMD`` nor ``GenuineIntel`` has none. Any input that cannot be read is an error, never a zero.

A temporary CUID is node-local: it names a component only on the installation whose machine-id produced it, and only while the component stays at the same PCIe address or socket. It changes when the machine-id changes or the component moves, and a same-model replacement in the same slot gets the same value.

.. _cuid-machine-id:

Machine identity and containers
-------------------------------

The library reads the machine-id from ``/etc/machine-id``, and from ``/var/lib/dbus/machine-id`` only when ``/etc/machine-id`` does not exist. An ``/etc/machine-id`` that is empty, ``uninitialized`` or all zero counts as no machine-id. Every temporary CUID needs the machine-id. Without one ``S`` reduces to properties of the hardware model and its slot, so two identically configured hosts would report the same temporary CUID for different physical parts; the library therefore reports an **error** rather than a placeholder for every component. Every container started from an image that bakes in a machine-id reports the same temporary CUIDs for the same device in the same slot, on every host. Give the container the host's ``/etc/machine-id``, for example with a read-only bind mount.

.. _cuid-gpu-partitions:

GPU partitions
==============

A GPU split into ``n >= 2`` compute partitions has one component per partition beside the whole GPU. Partition ``k`` (``0 <= k < n``, the partition's xcp id) has UnitID ``n*(n-1)/2 + 1 + k``: DPX 2 and 3, TPX 4 to 6, QPX 7 to 10, CPX on 6 XCCs 16 to 21, CPX on 8 XCCs 29 to 36. The whole GPU has UnitID 0, and a GPU in SPX is the whole GPU alone, with no separate partition. A partition uses its parent's PCIe address and IDs.

The library reads a partition's UnitID from its ``cuid_unit_id`` where amdgpu publishes one. Otherwise it reads the KFD topology under ``/sys/class/kfd/kfd/topology/nodes``, which any user can read: the node whose ``drm_render_minor`` is the partition's render node gives the parent as ``domain`` and ``location_id & ~7``, and ``k = location_id & 7``; ``n`` is the number of GPU nodes with that parent, and their indices must be exactly ``0`` to ``n-1``. A partition whose UnitID cannot be determined, for example because KFD is not loaded, has no CUID.

NIC functions
=============

A NIC's UnitID is its PCI function number. The functions of a multi-port card
can report one serial number, and the function number keeps their CUIDs
apart. Function 0 has UnitID 0, so a single-function NIC is unaffected. Two
components whose derived CUIDs coincide anyway are identified by neither: both
are left out of the inventory, a lookup of either fails with
``AMDCUID_STATUS_INVALID_FORMAT``, and every other component is still listed.

GPU route resolution
====================

For a whole PCI GPU, the BDF, ``/dev/dri/renderD*``, DRM class render/card
paths, PCI bus paths and their ``/sys/devices`` paths resolve to the same
component when live sysfs topology confirms they are the same device. The
render node is preferred, then the card node, then the PCI directory for a
display-class device without DRM nodes.

In a mode with two or more partitions the GPU's own render and card nodes
belong to partition 0, which is selected through its ``device/xcp`` node, and
the whole GPU is named by its BDF or PCI directory. Other XCP DRM nodes resolve
to their own ``xcp`` node. A parent BDF never stands in for a partition.
