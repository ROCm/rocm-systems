## Introduction
Managing hardware devices (GPUs, CPUs, NICs) in data centers often requires multiple tools, each with its own device identification method. This inconsistency complicates device correlation and management, especially across different vendors. The **Component Unified Identifier (CUID)** solves this by providing a deterministic, unique identifier for each device type, enabling consistent referencing and easier integration.

### What is CUID?

The **Component Unified Identifier (CUID or CUUID)** is generated by combining device-specific data into a 122 bit ID value as follows:

| Bits | Name | Comments |
|------|------|----------|
| 0:63 | Device Serial Number/Fingerprint | from PCIe configuration DSN caps (endpoint), SMBIOS platform serial number, ACPI or other architectural component identifier (if not available, SW generated fingerprint from proprietary individual marker) Integer, may be MSB 0-extended if smaller than 64 bit or truncated if larger |
| 64:71 | UnitID (part 1) | if component supports unitID, 0 otherwise |
| 72:79 | RevisionID | if component supports revision ID, 0 otherwise |
| 80:95 | DeviceID | from PCIe configuration space or SMBIOS ID, For CPU: Family # and Model # values combined |
| 96:111 | VendorID | from PCIe configuration space or SMBIOS vendor ID, follows PCIe vendor ID 16 bit value definition (e.g. 0x1022 or 0x1002 for AMD) |
| 112:116 | UnitID (part 2) | if UnitID value is >= 256, 0 otherwise; UnitID is 13 bits total, split across 64:71 and 112:116 |
| 117 | Auxiliary Value Identifier | 1 when bits 0:63 hold a synthesized auxiliary identity rather than a genuine serial; not part of UnitID; carried unchanged into the derived CUID |
| 118:121 | Component Type | See `amdcuid_device_type_t` in amd_cuid.h, which uses the on-wire values directly |

Component Type uses these values: `0x0` Platform, `0x1` CPU, `0x2` GPU, `0x3` NIC, `0x4` NPU, `0x5` Storage, `0x6` Memory, `0x7` generic PCIe device, `0x8` generic component, `0x9` rack tray, `0xA` rack, `0xB`–`0xE` reserved, `0xF` other. The field spans an octet boundary: its low two bits are the top two bits of payload octet 14, and its high two bits are the low two bits of payload octet 15. A producer that drops payload bits 120:121 therefore renders the type modulo 4 and collides an NPU with a Platform.

`amdcuid_device_type_t` names all sixteen of those values, not only the five this library can discover for itself. A Component Type also arrives from identifiers this library did not produce, such as a kernel-published `cuid_primary` or one another producer emitted, so a Storage or Rack component has to decode to a name rather than to an unnameable integer. `0xB`–`0xE` are reserved and have **no enumerator**. Because the valid range is therefore not contiguous, there is no `AMDCUID_DEVICE_TYPE_LAST` sentinel. Test a value with the header-only helper instead:

```c
if (!amdcuid_device_type_is_valid(type)) { /* reserved, or not a Component Type at all */ }
```

`amdcuid_device_type_is_valid()` is true for `0x0`–`0xA` and `0xF`, and false for the reserved `0xB`–`0xE`, for `AMDCUID_DEVICE_TYPE_NONE` (`0xFF`, deliberately outside what a 4-bit field can hold), and for anything else. The library version is 2.2 (`AMDCUID_LIB_VERSION_MAJOR`, `AMDCUID_LIB_VERSION_MINOR`); code that loops over Component Types uses the helper.

This value is then used to fill out a UUIDv8 style format as follows:

| Bit position | Value | Comments |
|--------------|-------|----------|
| 0:47 | ID value (part 1) | LSB of ID value |
| 48:51 | must be 8 (fixed) | for RFC 9562 compliance |
| 52:63 | ID value (part 2) ||
| 64:65 | 10b (fixed) | for RFC 9562 compliance |
| 66:127 | ID value (part 3) | MSB of ID value |

The version and variant bits are **inserted**, not overwritten: they displace the payload after them. The framing preserves payload bits 0 through 121 and discards exactly payload bits 122 through 127, which are always zero, so the payload recovers from the rendered UUID exactly. The bit positions are numbered MSB-first over the rendered octets, so the least significant payload octet appears at the **front** of the printed string: payload `d4abaad39b34c5060000a37302108000` renders as `d4abaad3-9b34-8c50-9800-028dcc084200`.

A **derived CUID** is derived by hashing the primary CUID using HMAC-SHA2-256 (keyed hash) with a 256-bit key. The key is the HMAC key and the 16 packed primary payload octets are the message. The digest folds into the derived payload as `digest[0:63]` → bits 0:63, reserved zero at 64:71, `digest[64:108]` (45 bits) → bits 72:116, bit 117 copied from the primary, reserved zero at 118:121.

Where no genuine serial number is reachable, or the caller has no node key, the library constructs a **temporary CUID**: the same layout, Component Type numbering, UUIDv8 framing and derivation, with the auxiliary bit (bit 117) set. amd-smi reports it as `auxiliary` (`AUXILIARY: True`). The version nibble is always `8`; a consumer tests bit 117 rather than branching on the UUID version. Because the derivation is keyed, a consumer without the key can neither recover the primary payload nor confirm a guess at it.

A temporary CUID is built by the device class that can build one, out of attributes that actually name the device. When even that is impossible, whether from no serial, no usable attributes, or no machine identity on the host, the library **returns an error** rather than a placeholder. The kernel takes the same position: with no serial it publishes nothing. Callers must handle the error rather than assume an identifier always comes back. Derivation requires a 256-bit HMAC key (FIPS 198-1). Anyone holding the key can confirm a guessed serial number, so the key carries the same handling requirements as the serial it protects: random, unique per deployment, and readable only by root.

### GPUs and the node key

A GPU or compute partition is driver-published when amdgpu exposes
`cuid_unit_id` (0444) in its sysfs directory: `/sys/bus/pci/devices/<bdf>` for
a whole GPU, the partition's `xcp` directory for a partition. Its primary CUID
is then the driver's `cuid_primary` (0400, `CAP_SYS_ADMIN`), which only root
can read.

A derived CUID that is not temporary needs a node-wide 256-bit key that other
local users cannot read. This library holds no node key, so every derived CUID
it returns is a **temporary CUID**, built from non-privileged information:
CPUs, NICs, NPUs, the platform and whole GPUs alike, for root and every other
caller. A partition has no temporary CUID, because every partition of a GPU
shares its parent's routing information, so the library returns no handle for
it. amd-smi reports the whole GPU's CUID for a GPU in SPX, whose one partition
covers every XCC.

Temporary CUIDs are keyed with the host's machine-id, so they are node-local.
See [Temporary CUIDs](docs/conceptual/what_is_cuid.rst) for the construction
and its effect on containers.

### Using the library

`libamdcuid_static.a` is a static library with one header, `amd_cuid.h`
(installed under `include/amdcuid`), and a CMake package that puts that
directory on the include path:

```cmake
find_package(amdcuid CONFIG REQUIRED)
target_link_libraries(my_tool PRIVATE amdcuid::amdcuid)
```

A program that links it carries no runtime dependency on CUID. It discovers
hardware, constructs primary CUIDs, derives the rest, and answers queries by
handle; [`example/main.cc`](example/main.cc) walks through the API. amd-smi
links the same library and is the administrator's interface to CUID:
`amd-smi node --cuid` lists every component's CUID.

### Build and Install Instructions

To build and install the library:

```sh
mkdir build
cd build
# Set CMAKE_INSTALL_PREFIX as needed (default is typically /opt/rocm/core)
cmake -DCMAKE_INSTALL_PREFIX=/opt/rocm ..
make
# Use sudo if installing to a system prefix like /opt
sudo make install
```

If users need to uninstall the CUID project, they can do so with the following instructions:

```sh
cd build
sudo make uninstall
```

A source install of 2.0, which shipped the `amdcuid` daemon, leaves the
daemon, `amdcuid_tool`, its configuration and its systemd unit behind when 2.2
is installed over it, because this release's install manifest does not list
them. Run `sudo make uninstall` in the old build tree first. The `.deb` and
`.rpm` packages remove them on upgrade.

Documentation can be built using the following instructions:

```sh
pip install -r docs/sphinx/requirements.txt
sphinx-build docs docs/_build/html
```

#### Notes

- No third-party crypto dependency: SHA-256 and HMAC-SHA-256 are built from source out of the shared `shared/sha256` component, whose objects are absorbed into `libamdcuid_static.a`, so the archive defines the digest symbols rather than importing them, and the library links no TLS stack
- Root/administrator privileges are required for full functionality (ACPI tables, SMBIOS UUID, PCI config space access, and the driver-published primary CUID)
