## Purpose

The auxiliary CUID: the last-resort identifier for a component whose genuine
serial number is not reachable, built entirely from non-privileged information.
It is a normal UUIDv8 in the normal layout with one bit set, so a consumer needs
no second parser and no branch on the UUID version.

## ADDED Requirements

### Requirement: Auxiliary CUIDs are uniform UUIDv8

An auxiliary CUID SHALL use the same 122-bit payload layout, the same component
type numbering, the same UUIDv8 framing and the same derivation as any other
CUID. It SHALL be distinguished solely by bit 117 of the payload, the Auxiliary
Value Identifier, being set.

A producer SHALL NOT emit an auxiliary CUID with a UUID version nibble other
than `8`, and SHALL NOT use the version nibble to signal that a value is
auxiliary.

Three consequences follow, and are normative:

- The format does not use UUIDv5. RFC 9562 defines version 5 as SHA-1 over
  `namespace ‖ name`; the CUID payload is HMAC-SHA-256 over a defined structure.
  A producer SHALL NOT emit a constructed CUID claiming version 5. A consumer
  still SHALL NOT reject a value on its version nibble, because an adopted
  firmware-supplied UUID legitimately carries version 1, 3, 4 or 5 and is
  adopted verbatim.
- A consumer parses every constructed CUID payload with one code path and one
  mask. It MAY read the version nibble to tell an adopted UUID from a
  constructed payload, which is what the layout requires of it, but SHALL NOT
  treat an unrecognised version as a reason to discard the value.
- The same device presents the same UUID version regardless of the privilege of
  the caller or the host it is enumerated on.

#### Scenario: A consumer identifies an auxiliary value

- **WHEN** a consumer reads any CUID
- **THEN** it determines whether the value is auxiliary by testing payload
  bit 117
- **AND** the version nibble is `8` in both cases

#### Scenario: No separate parser is required

- **WHEN** a consumer parses a mixed set of canonical and auxiliary CUIDs
- **THEN** every value decodes under the same layout
- **AND** no value is discarded on account of its version nibble

### Requirement: Auxiliary CUIDs are generated by user-mode software only

An auxiliary CUID SHALL be generated only by user-mode software, and only as a
last resort when kernel infrastructure that could supply a genuine identifier is
absent.

A kernel producer SHALL NOT generate an auxiliary CUID and SHALL NOT set
bit 117. Where a kernel producer has a serial number it publishes a genuine
primary; where it does not, it publishes nothing.

The auxiliary construction depends on the OS machine identity, which a kernel
driver cannot read, so a kernel-side auxiliary CUID would disagree with the
user-mode one by construction.

#### Scenario: A kernel-published CUID is never auxiliary

- **WHEN** a CUID is read from a kernel interface
- **THEN** payload bit 117 is clear

#### Scenario: A component with no reachable serial publishes nothing in the kernel

- **WHEN** a kernel producer can find neither a device serial nor a PCIe Device
  Serial Number for a component
- **THEN** it does not register a CUID for that component

### Requirement: Auxiliary input structure

The auxiliary serial SHALL be derived from a 256-bit input structure, packed
LSB-first into 32 octets, with the following field positions:

| Bits | Width | Field |
|---|---|---|
| 0:15 | 16 | Format: `1` = PCIe device, `2` = CPU, others reserved |
| 16:143 | 128 | Machine ID |
| 144:175 | 32 | PCIe Routing ID |
| 176:183 | 8 | Revision ID |
| 184:199 | 16 | Device ID |
| 200:215 | 16 | Vendor ID |
| 216:219 | 4 | Component Type |
| 220:255 | 36 | Reserved, SHALL be zero |

The widths SHALL sum to exactly 256, and every field a producer has to read or
write as a value SHALL be a whole number of octets, octet-aligned. The two
exceptions are the trailing pair: Component Type occupies the low nibble of
octet 27, and the 36-bit reserved field is that octet's high nibble together
with octets 28:31. Both SHALL be zero-extended into octet 27, so a producer
packs one octet there and four zero octets after it.

*S1's published ranges also sum to 256, so the defect is not arithmetic: they
give Format 17 bits (`0-16`) and Machine ID 127 (`17-143`). A 17-bit field is
not a whole number of octets, and a 127-bit Machine ID cannot hold the 128-bit
`/etc/machine-id` the same row names. Moving the boundary one bit fixes both,
and leaves every field an implementer has to marshal on an octet boundary.*

The Machine ID SHALL be 128 bits: on Linux, the 32 hexadecimal characters of
`/etc/machine-id` decoded to 16 octets, octet `k` of the decoded value occupying
structure bits `16 + 8k` through `23 + 8k`. A producer that cannot obtain a
machine identity SHALL NOT emit an auxiliary identifier at all. Packing zero
there instead would give two identically configured hosts the same auxiliary
identifier for their corresponding components.

The PCIe Routing ID SHALL be `(segment << 16) | (bus << 8) | (device << 3) |
function`, and SHALL be zero for the CPU Format, which has no Bus/Device/
Function of its own.

Every field SHALL carry the same meaning it carries in the primary payload
layout, for every Format. For the CPU Format that means Revision holds the
CPUID stepping, **Device holds Family and Model combined** exactly as the
primary layout defines for a CPU, and **Vendor holds the CPU vendor ID**.

*S1's separate CPU table splits Family and Model into two 16-bit fields and
places FamilyID at bits 200:215, which is the Vendor field in both the PCIe
structure and the primary layout, leaving a CPU auxiliary value with no vendor at
all. One structure with one meaning per field removes the question.*

Component Type SHALL use the on-wire numbering, the same values as the primary
payload's Component Type field.

A producer SHALL NOT derive the structure from a formatted string, and SHALL NOT
filter, normalise or otherwise transform the field values before packing them.

*The prohibition is specific. One producer builds its input by concatenating a
BDF string with a machine ID and then removing every character that is not a
hexadecimal digit. That erases the separators, so `0000:65:00.0` and
`0000:65:0:00.0` collapse to the same input, and a CPU seed of `"socket:" + id`
degenerates to the constant `cce` followed by the digits. Fixed-width binary
fields have no such failure mode.*

#### Scenario: The ranges sum

- **WHEN** the input structure's field widths are added
- **THEN** the total is 256 bits with no gap and no overlap

#### Scenario: Every marshalled field is octet-aligned

- **WHEN** a producer packs the structure
- **THEN** Format, Machine ID, Routing ID, Revision, Device and Vendor each
  begin and end on an octet boundary
- **AND** Component Type is the low nibble of octet 27, with the rest of that
  octet and octets 28:31 zero

#### Scenario: Two functions of one device differ

- **WHEN** the auxiliary serial is computed for `0000:65:00.0` and for
  `0000:65:00.1` on the same machine
- **THEN** the two Routing ID fields differ
- **AND** the two auxiliary serials differ

### Requirement: Auxiliary serial

The auxiliary serial SHALL be the first 8 octets of the unkeyed SHA-256 digest
of the 32-octet input structure, interpreted as a little-endian 64-bit value,
and SHALL be placed in payload bits 0:63 of an otherwise normal primary payload
with bit 117 set.

The remaining primary fields (UnitID, Revision ID, Device ID, Vendor ID and
Component Type) SHALL be populated from the component's real identity exactly as
they are for a canonical primary.

An auxiliary CUID is ambiguous by construction. It is stable only while the OS
installation and the device topology are unchanged, and it is not guaranteed
unique across nodes. Bit 117 exists so that a consumer can tell it apart before
relying on it.

#### Scenario: Auxiliary and canonical primaries differ only in bits 0:63 and 117

- **WHEN** a component's canonical and auxiliary primary payloads are compared
- **THEN** they agree in the Revision, Device, Vendor, UnitID and Component Type
  fields
- **AND** they differ in the serial and in bit 117

#### Scenario: A reinstalled OS changes the auxiliary value

- **WHEN** the machine ID changes and the auxiliary CUID is recomputed
- **THEN** the auxiliary primary and its derived value both change

### Requirement: Auxiliary derivation carries bit 117

The derived value of an auxiliary primary SHALL be computed as
`HMAC-SHA256(key = the temporary fixed key, message = the 16 auxiliary primary
octets)`, folded into the derived layout by the same rule as any other derived
CUID, with bit 117 copied from the auxiliary primary.

Because bit 117 is carried, a derived auxiliary CUID SHALL be identifiable as
auxiliary without reference to its primary.

#### Scenario: The auxiliary marker survives derivation

- **WHEN** a derived CUID is computed from an auxiliary primary
- **THEN** payload bit 117 of the derived value is set

*A producer that passes a fixed constant as the derivation message instead of
the auxiliary primary reads bit 117 out of that constant, and so emits a derived
auxiliary CUID that is not marked auxiliary. This has occurred in practice.*
