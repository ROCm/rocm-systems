# HIP Loader Research

This document records local priors and relevant loader/linker behavior for the
HIP loader design. Paths are relative to the workspace root unless otherwise
noted.

## Current HIP And CLR State

The current HIP runtime is built by CLR:

* TheRock configures the HIP runtime as the `hip-clr` subproject from
  `sources/TheRock/rocm-systems/projects/clr`.
* CLR builds a target named `amdhip64`.
* On Linux, the shared library output name is `amdhip64` with `SOVERSION` set to
  the HIP major.
* On Windows, CLR currently uses a runtime output name derived from
  `amdhip64_${HIP_VERSION_MAJOR}`.
* Linux exports are controlled by
  `rocm-systems/projects/clr/hipamd/src/hip_hcc.map.in`.
* Windows exports are controlled by
  `rocm-systems/projects/clr/hipamd/src/amdhip.def.in`.
* `hip_version.h` is generated by CLR CMake from
  `rocm-systems/projects/hip/VERSION`.

The checked-in HIP API header
`rocm-systems/projects/hip/include/hip/hip_runtime_api.h` currently pushes
default GCC visibility around the API region and declares public functions as
plain names, for example:

```c
hipError_t hipInit(unsigned int flags);
hipError_t hipDriverGetVersion(int* driverVersion);
hipError_t hipRuntimeGetVersion(int* runtimeVersion);
```

There is no consistent per-declaration macro today that can change the public
function name by ABI mode. Existing compatibility aliases already appear in the
header, for example:

```c
#define hipGetDeviceProperties hipGetDevicePropertiesR0600
#define hipDeviceProp_t hipDeviceProp_tR0600
#define hipChooseDevice hipChooseDeviceR0600
```

The installed ROCm tree linked from the workspace currently has:

* `rocm/lib/libamdhip64.so`
* `rocm/lib/libamdhip64.so.7`
* `rocm/lib/libamdhip64.so.7.13.60850-ed975342ae`

The installed Linux DSO has SONAME `libamdhip64.so.7` and exports HIP symbol
versions through the current HIP 7 line. Local inspection found global exports
for public `hip*` and `__hip*` entry points, profiler extension symbols, and a
small number of C++-mangled launch symbols.

Local relocation inspection also found self-PLT relocations from the installed
`libamdhip64.so.7` to public HIP exports, including:

* `hipGetDevice`
* `hipGetDevicePropertiesR0600`
* `hipRegisterTracerCallback`
* `hipMemcpyAsync`
* `hipCreateChannelDesc`

This matters because a backend that exports public `hip*` names can accidentally
bind internal calls to an earlier global symbol with the same name, including
the loader or an `LD_PRELOAD` interposer.

## Existing Historic Compatibility Prior

Current HIP already carries a small but important compatibility model for older
device-property ABI shapes. This is the best local precedent for historic public
ABI loaders.

The public header currently aliases the unqualified names to the HIP 6-compatible
symbols:

```c
#define hipGetDeviceProperties hipGetDevicePropertiesR0600
#define hipDeviceProp_t hipDeviceProp_tR0600
#define hipChooseDevice hipChooseDeviceR0600
```

The deprecated header keeps the older `hipDeviceProp_tR0000` layout and declares
the older entry points:

```c
hipError_t hipGetDevicePropertiesR0000(hipDeviceProp_tR0000* prop, int device);
hipError_t hipChooseDeviceR0000(int* device, const hipDeviceProp_tR0000* prop);
```

The Linux version script and Windows DEF file export both old and newer symbols.
For example, `hip_hcc.map.in` exports `hipChooseDevice`,
`hipChooseDeviceR0000`, `hipGetDeviceProperties`, and
`hipGetDevicePropertiesR0000` in the older `hip_4.2` node, then adds
`hipChooseDeviceR0600` and `hipGetDevicePropertiesR0600` in the `hip_6.0` node.
The map also records the later HIP 6 lineage through nodes such as `hip_6.1`,
`hip_6.2`, `hip_6.4`, and `hip_6.5`.

CLR implements this by hand:

* `hipGetDevicePropertiesR0600` fills the current `hipDeviceProp_tR0600` layout.
* `hipGetDevicePropertiesR0000` separately fills the older
  `hipDeviceProp_tR0000` layout.
* `hipChooseDeviceR0600` and `hipChooseDeviceR0000` share templated selection
  logic over the two property layouts.
* The plain `hipGetDeviceProperties` and `hipChooseDevice` compatibility exports
  forward to the `R0000` versions.
* `hipGetProcAddress_common` maps public string lookups for
  `hipGetDeviceProperties` and `hipChooseDevice` to the `R0600` symbols when the
  requested HIP version is at least 600.

This prior argues against trying to fully automate ABI adaptation. The changed
symbols are few relative to the whole API, but the details are semantic:
structure fields appear, disappear, move, or need different defaults. Metadata
should identify the affected symbols and route to named compatibility functions;
human-authored C++ should own the actual layout and signature conversion.

For a loader implementation, this prior should be inverted compared to current
CLR. Current CLR exports and implements both `R0000` and `R0600` runtime
variants in the backend itself. A historic loader should instead implement old
public variants in the loader and call only the newest backend ABI. For example,
a HIP 6 public loader should implement `hipGetDeviceProperties` and
`hipGetDevicePropertiesR0000` by calling the newest backend device-property
entry point, then converting the newest returned layout to `hipDeviceProp_tR0000`
in loader code. It should not require or resolve a backend
`hipBackendV*GetDevicePropertiesR0000` symbol.

For a HIP 6 loader proof of concept, the initial archaeology should start from:

* `projects/hip/include/hip/hip_runtime_api.h` compatibility aliases.
* `projects/hip/include/hip/hip_deprecated.h` historic layout definitions.
* `projects/clr/hipamd/src/hip_hcc.map.in` and
  `projects/clr/hipamd/src/amdhip.def.in` exported public symbols.
* `projects/clr/hipamd/src/hip_device.cpp` and
  `projects/clr/hipamd/src/hip_device_runtime.cpp` manual compatibility code.
* Available ROCm 6 release headers or tags for validating the exact public
  source and binary contract.

The checked-in HIP 7 change document is another useful input because it lists
the kinds of changes a manifest must classify. Examples include behavior changes
such as `hipGetLastError` and `hipPointerGetAttributes`, removal of `hipRTC`
symbols from the HIP runtime library, signature changes such as `hipMemcpyHtoD`
and `hipCtxGetApiVersion`, and a `hipMemsetParams` layout change. Not all of
these require binary loader shims, but the metadata needs to distinguish binary
ABI changes, source compatibility changes, behavior changes, and removed
exports.

## ROCm 6.4.4 To 7.0.0 Archaeology

The `rocm-systems` repository available in this workspace has local release tags
only for ROCm 7.x. For the HIP 6 to HIP 7 boundary, the archaeology used
temporary read-only clones of the split upstream repositories:

* `https://github.com/ROCm/HIP.git`
* `https://github.com/ROCm/clr.git`

The comparison was `rocm-6.4.4..rocm-7.0.0`, with spot checks against the
current checked-in `rocm-systems` source and the installed
`rocm/lib/libamdhip64.so.7`.

### Linux Version Nodes

`ROCm/clr` `rocm-6.4.4` has Linux HIP version nodes through `hip_6.4`:

```text
hip_4.2 -> hip_4.3 -> hip_4.4 -> hip_4.5 -> hip_5.0
  -> hip_5.1 -> hip_5.2 -> hip_5.3 -> hip_5.5 -> hip_5.6
  -> hip_6.0 -> hip_6.1 -> hip_6.2 -> hip_6.4
```

`ROCm/clr` `rocm-7.0.0` does not add a `hip_7.0` node. Instead, it adds a
`hip_6.5` node containing:

* `hipLaunchKernelExC`
* `hipDrvLaunchKernelEx`
* `hipMemGetHandleForAddressRange`

This appears to reflect the release history: the engineering ABI lineage was
effectively a HIP 6.5 line, while the product release became ROCm/HIP 7.0. The
loader should preserve that history exactly. It should not invent a `hip_7.0`
node or renumber old nodes to make them look consistent with the product major.

The current `rocm-systems` map extends the chain with `hip_7.1`, `hip_7.2`,
`hip_profiler_ext`, and `hip_7.14`. The installed current
`libamdhip64.so.7` reports those exact nodes in `readelf --version-info`.

Important consequences for the loader:

* Linux symbol-version node names are an ABI contract and must be generated from
  per-public-major baselines, not inferred from the loader SONAME major.
* A HIP 7 public loader may contain no `hip_7.0` node even though it is a HIP 7
  SONAME.
* A symbol can keep the same version node while its source-level contract changes
  across SONAME majors. For example, `hipDrvGraphAddMemsetNode@@hip_5.6` uses an
  old pointed-to struct contract in HIP 6 and a different pointed-to struct
  contract in HIP 7.
* CI should verify the actually exported dynamic symbols and version nodes from
  the built loader DSO. The version script can contain stale names that are not
  present in the binary.

### Windows DEF Files

The split `ROCm/clr` `rocm-6.4.4` Windows DEF file is
`hipamd/src/amdhip.def`. It has no version nodes and contained a malformed
entry:

```text
hipLinkDestroyhipEventRecordWithFlags
```

`rocm-7.0.0` fixes this into separate `hipLinkDestroy` and
`hipEventRecordWithFlags` entries and adds `hipLaunchKernelExC` and
`hipDrvLaunchKernelEx`. At `rocm-7.0.0`, the Windows DEF did not list
`hipMemGetHandleForAddressRange` even though the Linux `hip_6.5` node did. The
current `rocm-systems` source uses `amdhip.def.in` and has continued to diverge
from the 7.0.0 DEF baseline.

Loader generation should therefore keep platform-specific public-major baselines
instead of assuming Linux version scripts and Windows DEF files contain the same
symbol set.

### Concrete 6 To 7 Changes

The tag comparison and commit trail identified these loader-relevant changes:

* `hipGetDeviceProperties` / `hipChooseDevice`: current headers alias public
  source names to `R0600` symbols, while old `R0000` symbols remain exported.
  Commit `b006380ff` changed current CLR use sites to prefer the new API. A HIP 6
  loader should implement legacy `R0000` exports itself and call only the newest
  backend device-property API.
* `hipDrvGraphAddMemsetNode@@hip_5.6` and
  `hipDrvGraphExecMemsetNodeSetParams@@hip_6.2`: commit `968f5599a` removed the
  old `HIP_MEMSET_NODE_PARAMS` public struct from the HIP 7 header path and
  changed these APIs to take `const hipMemsetParams*`. The public symbol names
  and Linux version nodes did not change, so a HIP 6 loader needs manual
  conversion from `HIP_MEMSET_NODE_PARAMS` to the newest backend
  `hipMemsetParams`.
* `hipCtxGetApiVersion@@hip_4.2`: commit `ee2d4a035` changed the source
  signature from `int*` to `unsigned int*`. The C ABI is still a pointer-sized
  argument, but `HIP_API_VERSION=6` header mode and profiler metadata need the
  old source type.
* `hipMemcpyHtoD@@hip_4.2` and `hipMemcpyHtoDAsync@@hip_4.2`: the source
  signature changed from `void* src` to `const void* src`. This is source and
  C++ type compatibility metadata; the C ABI is not meaningfully different.
* `hipPointerGetAttributes@@hip_4.2`: commit `0b64eec92` changed null-pointer
  handling to match CUDA 11+ behavior. A HIP 6 loader can preserve older behavior
  with a small precondition wrapper before calling the newest backend.
* `hipFree@@hip_4.2`: commit `58df22546` disabled implicit waiting in `hipFree`
  for async allocations. A HIP 6 loader may need a conservative synchronization
  wrapper before dispatch when preserving old behavior matters.
* `hipFreeAsync@@hip_5.1`: commits `d00a0db3d` and `cddddc79b` changed null
  pointer handling to return `hipSuccess`. A HIP 6 loader can preserve older
  `hipErrorInvalidValue` behavior with a precondition wrapper.
* `hipGetLastError@@hip_4.2` / `hipExtGetLastError@@hip_6.0`: the HIP 7 change
  document describes the CUDA-aligned `hipGetLastError` behavior and points old
  behavior at `hipExtGetLastError`. The direct `hip_error.cpp` wrapper body is
  not the whole story; compatibility metadata should still classify this as a
  behavior compatibility record for old public majors.
* `hiprtc*` runtime exports: `rocm-6.4.4` Linux version scripts list `hiprtc`
  symbols in `hip_4.2` and `hiprtcGetBitcode` / `hiprtcGetBitcodeSize` in
  `hip_5.3`. Commit `e9dbd7c99` removed hipRTC sources from `amdhip64`, and the
  installed current `libamdhip64.so.7` does not export `hiprtc*` despite stale
  map entries. A HIP 6 loader that promises binary compatibility may need
  loader-owned `hiprtc*` compatibility exports that forward to `libhiprtc`.
* `hiprtcCreateProgram` and `hiprtcCompileProgram`: commit `e5f7519e6` changed
  hipRTC signatures to use `const char* const*` arrays. This is relevant if the
  HIP 6 loader carries old `hiprtc*` exports or if header version selection
  covers hipRTC.
* `hipLaunchKernelExC`, `hipDrvLaunchKernelEx`, and
  `hipMemGetHandleForAddressRange`: commits `8c6b90996` and `12131de4a` added
  these as Linux `hip_6.5` exports at the 7.0 boundary. They are additions, not
  old-major compatibility shims.

The prototype builds a replacement HIP library that loads a real backend library
with `dlopen`, fills a HIP function table with `dlsym`, and optionally loads an
interceptor. Important environment variables include:

* `HIP_PASSTHROUGH_BACKEND_LIB`
* `HIP_PASSTHROUGH_INTERCEPTOR`
* `HIP_LOG_FILE`
* `HIP_LOG_LEVEL`
* `HIP_TRACE_FILE`
* `HIP_TRACE_LEVEL`

The passthrough prior explicitly handles compiler-private HIP ABI symbols:

* `__hipRegisterFatBinary`
* `__hipUnregisterFatBinary`
* `__hipRegisterFunction`
* `__hipRegisterVar`
* `__hipRegisterManagedVar`
* `__hipRegisterSurface`
* `__hipRegisterTexture`
* `__hipPushCallConfiguration`
* `__hipPopCallConfiguration`

The first four are included in the smaller passthrough map. The full passthrough
map includes the broader compiler-private set and `__hipGetPCH`.

Useful ideas:

* A single function table is a practical boundary between the exported ABI and
  the implementation.
* Interceptors can be represented as table-to-table transforms.
* Loader-level logging and tracing can be implemented without changing backend
  internals.

Limitations:

* The manually maintained table and minimal type definitions do not scale to
  multi-major HIP API compatibility.
* The generated stubs are based on existing binary symbols, not a source-of-truth
  API manifest.
* Generic variadic stubs are not a safe long-term ABI implementation strategy.
* The prototype relies on replacing the public library rather than owning a
  formal public loader ABI.
* It does not solve backend public-symbol collisions.

## Vulkan Loader Prior

The local Vulkan Loader clone is at:

```text
/srv/vm-shared/projects/therock-workspace2/sources/Vulkan-Loader
```

Relevant documentation:

* `docs/LoaderInterfaceArchitecture.md`
* `docs/LoaderApplicationInterface.md`
* `docs/LoaderDriverInterface.md`

Useful ideas:

* The loader owns the public application ABI.
* Drivers expose a private loader-driver entry point, not the whole public
  application ABI.
* Dispatch tables and trampolines are generated from a machine-readable API
  registry.
* Optional layers can intercept calls through dispatch tables.
* Loader environment variables are parsed carefully and restricted in elevated
  contexts.
* Linux uses a stable public SONAME major. Windows uses a versioned loader DLL
  name such as `vulkan-1.dll`.

The most important symbol-hygiene lesson is in the Vulkan driver interface:
drivers must not export public Vulkan command names that clash with the loader.
The HIP loader should adopt the same rule. A HIP backend should not be a second
`libamdhip64.so.N` exporting the same public `hip*` names as the loader.

Relevant source areas:

* `loader/trampoline.c` implements public trampolines and dispatch entry lookup.
* `loader/generated/vk_layer_dispatch_table.h` is generated dispatch-table
  structure.
* `scripts/generate_source.py` verifies generated output from the Vulkan XML
  registry.
* `loader/loader_environment.c` contains secure environment handling.
* `loader/log.c` implements option-based loader logging.
* `loader/unknown_ext_chain_gas_x86.S` contains efficient assembly dispatch
  stubs for unknown extension paths.

## Implib.so Prior

TheRock vendors Implib.so at:

```text
sources/TheRock/build_tools/third_party/implib
```

Upstream reference:

```text
https://github.com/yugr/Implib.so
```

Implib.so implements ELF delay-loading behavior similar to Windows import
libraries. It can generate assembly trampolines and initialization code that
lazy-loads a target library and then redirects calls through a resolved table.

Useful ideas:

* Generated assembly trampolines can get close to PLT overhead.
* A generated wrapper library can hide `dlopen` and `dlsym` mechanics from
  callers.
* The library already has architecture-specific trampoline templates.
* Its documentation covers reduced and renamed library interfaces.

Limitations for HIP:

* It does not handle ELF symbol versions, which are required for public
  `libamdhip64.so.N` compatibility.
* It does not directly solve multi-major HIP struct and signature adaptation.
* It is primarily a symbol-level delay loader, while HIP needs a generated API
  model and compatibility shims.
* It does not remove the need for backend symbol hygiene.

Implib.so is a useful implementation reference for fast dispatch and possibly
for generated backend wrappers. It should not be the sole source of truth for
the HIP public ABI.

## Header Symbol Renaming Techniques

The design needs a portable way for HIP headers to declare public names in
public mode and backend names in backend mode.

Preferred technique:

```c
hipError_t HIP_API_SYMBOL(Init)(unsigned int flags);
```

In public mode, `HIP_API_SYMBOL(Init)` expands to `hipInit`. In backend mode, it
expands to a versioned private symbol such as `hipBackendV8Init`.

This is more maintainable than:

* Per-function `#if HIP_ABI_MODE ...` blocks.
* Global public-name replacement such as `#define hipInit hipBackendV8Init`.
* Full declaration-swallowing macros such as
  `HIP_API_DECL(hipError_t, Init, (unsigned int flags))`.

Relevant external mechanisms:

* GCC asm labels can assign an assembler symbol name to a declaration:
  https://gcc.gnu.org/onlinedocs/gcc/Asm-Labels.html
* GCC `#pragma redefine_extname` can rename an external declaration:
  https://gcc.gnu.org/onlinedocs/gcc/Symbol-Renaming-Pragmas.html
* MSVC DEF files can export `entryname=internal_name`:
  https://learn.microsoft.com/lb-lu/cpp/build/reference/exports
* Apple `ld` supports symbol export lists and aliasing options:
  https://keith.github.io/xcode-man-pages/ld.1.html
* AIX `ld` supports import/export files and loader-section symbol controls:
  https://www.ibm.com/docs/ssw_aix_71/l_commands/ld.html

These mechanisms are useful for generated platform-specific export lists and
compatibility glue. They are not a good primary HIP header contract because they
do not define the source-level symbol name consistently across Linux, Windows,
MacOS, and AIX compilers.

## Profiler Generator Prior

The existing profiler generator is:

```text
rocm-systems/projects/clr/hipamd/src/hip_prof_gen.py
```

It currently:

* Uses regexes to find API declarations such as `hipError_t hipSetupArgument(...)`.
* Parses implementation sources and expects public API definitions.
* Uses `CppHeaderParser` for generated profiler enum information.
* Emits profiler API IDs, callback argument records, and string formatting.
* Is wired through CLR CMake by preprocessing `hip_runtime_api.h` and related
  headers.

This is fragile for a loader architecture. If the generator parses a backend-mode
preprocessed header, it could see backend symbols rather than canonical public
API names.

A `HIP_API_SYMBOL(Suffix)` declaration convention can improve this, but only if
tooling keys off the raw declaration form or a generated manifest. The generator
should treat the suffix as canonical API identity:

```c
hipError_t HIP_API_SYMBOL(Init)(unsigned int flags);
```

The canonical profiler name is `hipInit`, independent of whether the compiled
symbol is `hipInit` or `hipBackendV8Init`.

Immediate transition path:

* Keep existing profiler IDs public-name based.
* Run the old parser in public ABI mode until the manifest exists.
* Add a parser mode that recognizes `HIP_API_SYMBOL(Suffix)` in raw headers.

Long-term path:

* Generate profiler IDs and argument records from the HIP API manifest.
* Keep callback IDs stable across public and backend ABI modes.
* Store display strings and `hipGetProcAddress` names as canonical public names.

The current generated profiler data already treats some compiler-private
symbols, including `__hipPushCallConfiguration` and
`__hipPopCallConfiguration`, as traceable API IDs. The loader manifest should
keep these in a separate compiler-private ABI category rather than losing them
under a broad "not public API" filter.

## Compiler-private HIP ABI

HIP-Clang emits references to runtime entry points from generated host-side
constructors and destructors. The HIP porting guide documents that generated
initialization functions call `__hipRegisterFatBinary`,
`__hipRegisterFunction`, and `__hipRegisterVar`, and termination functions call
`__hipUnregisterFatBinary`.

Current CLR exports the compiler-private set in both the Linux version script
and Windows DEF file:

* `__hipPopCallConfiguration`
* `__hipPushCallConfiguration`
* `__hipRegisterFatBinary`
* `__hipRegisterFunction`
* `__hipRegisterVar`
* `__hipRegisterSurface`
* `__hipRegisterTexture`
* `__hipRegisterManagedVar`
* `__hipUnregisterFatBinary`

Current CLR implements these as extern "C" wrappers in
`projects/clr/hipamd/src/hip_table_interface.cpp` and dispatches them through a
compiler dispatch table. This is directly applicable to the loader design: the
loader should export the public compiler-private ABI names and forward to
loader-owned table entries resolved from private backend symbols.

These symbols are "private" in the sense that applications generally should not
call them directly. They are public dynamic-linker ABI symbols because
HIP-compiled user objects and DSOs may reference them.

## API Metadata And ABI Tooling

Existing local precedent:

* `rocm-systems/.github/workflows/abi-compliance-check.yml` is focused on
  AMDSMI.
* `projects/amdsmi/tests/abi_check/abi_check.py` compares headers and runs
  `abi-compliance-checker`.

That precedent is useful, but HIP needs stricter and broader tooling:

* HIP has many public functions, versioned symbols, and compatibility aliases.
* Future HIP majors may intentionally change signatures and structures.
* Backends should target the newest API while public older-major libraries
  remain compatibility shims.
* Header parsing must drive generated source, not just produce a report.
* Historic public ABI loaders need routing metadata that identifies only the
  ABI-breaking deltas requiring manual compatibility code.

Recommended source extraction:

* Use Clang AST output or libclang for types and declarations.
* Supplement with a small manifest annotation file for semantic metadata that is
  not obvious from C declarations.
* Avoid relying on regex parsing for ABI-critical generation.

Recommended generated artifacts:

* Public loader wrappers.
* Loader-side backend function-table types.
* Minimal backend metadata handshake declarations.
* Backend private symbol declarations.
* Symbol version scripts.
* Windows DEF files.
* API logging metadata.
* Compatibility shim code.
* Compatibility metadata coverage reports.
* Profiler callback IDs and argument records.

Recommended CI gates:

* Manifest diff for semantic-version rules within a major.
* ELF export and version-node diff using `readelf` or `llvm-readelf`.
* Windows export diff using `dumpbin` or `llvm-readobj`.
* Backend-mode forbidden public export check.
* Backend-mode relocation check for public HIP self-PLT references.
* Historic compatibility coverage checks for every carried public major.
* Generated output verification, similar in spirit to Vulkan's generated source
  verification.
* Binary ABI checks with `libabigail` or `abi-compliance-checker` where useful.

## Dynamic Linker And Namespace Findings

On Linux, `dlopen` with `RTLD_LOCAL` does not make a backend immune from symbol
interposition. It only prevents the backend's symbols from being made available
to subsequently loaded objects as a global lookup source.

`dlopen(3)` documents:

* `RTLD_LOCAL` keeps loaded symbols out of the global lookup scope for later
  loads.
* `RTLD_GLOBAL` makes loaded symbols available for later symbol resolution.
* A local object can be promoted if later loaded as a dependency of a global
  object.
* `RTLD_DEEPBIND` changes lookup priority for the loaded object on glibc, but it
  is not portable and can conflict with intended interposition and tooling.

Reference:

```text
https://man7.org/linux/man-pages/man3/dlopen.3.html
```

For HIP, this means:

* A backend exporting public `hip*` names can conflict with the loader exporting
  the same names.
* A backend's own PLT relocation to `hipMemcpyAsync` can bind to an earlier
  global `hipMemcpyAsync`, including the loader or an `LD_PRELOAD` library.
* `LD_PRELOAD` can interpose the application-to-loader boundary, which may be
  useful for diagnostics, but backend internals must not depend on public-symbol
  calls.
* A preloaded current HIP runtime can interpose public loader symbols and, in
  some cases, defeat expected loader policy.

`dlmopen` can isolate a library in a separate glibc link-map namespace, but it is
not a good default for HIP:

* It is Linux/glibc-specific.
* It can duplicate process-global dependencies such as HSA, ROCR, COMGR, and
  profiler registration libraries.
* It has namespace limits and complicated interactions with TLS and global
  runtime state.
* It does not address Windows, MacOS, or AIX.

The preferred rule is simpler: backend-mode DSOs do not export public HIP API
symbols, and loader-to-backend calls go through explicit function pointers
resolved from the selected backend handle after a minimal backend metadata
handshake confirms that the library is a compatible HIP loader backend.

## Research Conclusions

The loader should adopt the Vulkan-style ownership boundary:

* Public ABI symbols belong to the loader.
* Compiler-private ABI symbols used by HIP-Clang also belong to the loader.
* Backends expose a minimal identity handshake and private versioned symbols.
* The loader builds generated function tables from those private symbols.
* Generated metadata drives wrappers, exports, logging, profiler IDs, and ABI
  checks.

The HIP headers should grow an ABI-mode naming contract:

```c
hipError_t HIP_API_SYMBOL(Init)(unsigned int flags);
```

This keeps the source spelling close to normal C, gives generators a stable hook,
and avoids global macro replacement of public names.

The backend conversion is not just a SONAME rename. Unique SONAMEs avoid package
and loader collisions, but they do not by themselves prevent ELF symbol
interposition. Backend-mode symbol renaming and export checks are required.
