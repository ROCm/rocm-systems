# In-Memory Device Linker Architecture

## Overview

This document analyzes the feasibility of a new architecture for the device linker that eliminates most disk I/O by:
1. Compiling specialized kernels directly into memory buffers (LLVM/Clang APIs)
2. Having the device linker read directly from memory buffers
3. Precomputing final image layout for direct memcpy into mmap'd output
4. Potentially eliminating specialized kernel dispatcher code

## Current Architecture

The current pipeline for specialized kernels:

1. **CMake compiles** ~2580 specialized kernels via `hipcc` → individual `.o` files (~177MB total)
2. **Device linker** reads all `.o` files, extracts sections (`.text`, `.rodata`, `.note`, debug)
3. **Device linker** merges into single ELF → ~295KB output (600x reduction)
4. **Bundler + Host compile** wraps result into final object

The massive size reduction indicates most of the intermediate data (symbols, relocations, metadata) is discarded.

## Proposed Architecture Components

### 1. In-Memory Compilation via LLVM/Clang APIs

**Feasibility: MODERATE-HIGH complexity**

The AOMP LLVM provides the necessary APIs:

```cpp
// Key components available in /COD/LATEST/aomp/llvm/include:
clang::CompilerInstance       // Manages compilation
clang::EmitObjAction          // Generates object code
llvm::SmallVectorMemoryBuffer // In-memory output buffer
llvm::vfs::InMemoryFileSystem // Virtual filesystem for inputs
```

**Good points:**
- `SmallVectorMemoryBuffer` can hold compilation output without disk writes
- `CompilerInstance` supports `setVirtualFileSystem()` for inputs
- Parallel compilation possible within single process (shared LLVM context)
- Eliminates 177MB of intermediate disk writes

**Bad points:**
- HIP compilation is complex: requires AMD clang extensions, device bitcode linking (ocml.bc, ockl.bc), kernel descriptor generation
- Would need to replicate the exact `-cc1` invocation from `build_with_device_linker.sh`
- Linking against full libclang adds ~50-100MB to device_linker binary
- HIP compiler internals aren't designed for embedding; may have hidden state/globals

### 2. Device Linker Reads from Memory Buffers

**Feasibility: HIGH (already partially implemented)**

The device linker already uses LLVM's `MemoryBuffer`. Currently `parseKernel()` writes to a temp file then re-parses. This could be changed to:

```cpp
// Direct parsing from memory (no temp file needed)
auto buffer = llvm::MemoryBuffer::getMemBuffer(
    StringRef(reinterpret_cast<const char*>(elf_data.data()), elf_data.size()),
    "", false);
auto obj = llvm::object::ObjectFile::createObjectFile(buffer->getMemBufferRef());
```

**Good points:**
- Device linker already links LLVM libraries
- `llvm::object::ELFObjectFile` supports direct memory parsing
- Eliminates temp file I/O in `parseKernel()`

### 3. Precomputed Layout + mmap'd Output

**Feasibility: HIGH**

The device linker already does two passes. Converting to mmap'd output:

```cpp
// Precompute total size
size_t total_size = computeFinalElfSize();

// mmap output file
int fd = open(output_path, O_RDWR | O_CREAT | O_TRUNC, 0644);
ftruncate(fd, total_size);
uint8_t* output = (uint8_t*)mmap(nullptr, total_size, PROT_READ|PROT_WRITE, MAP_SHARED, fd, 0);

// Direct memcpy into output at precomputed offsets
memcpy(output + text_offset, merged_text.data(), merged_text.size());
memcpy(output + rodata_offset, merged_rodata.data(), merged_rodata.size());
// ...
```

**Good points:**
- Eliminates building large output vector in memory
- Kernel async write-back by OS
- Better memory usage for large outputs

**Bad points:**
- More complex error handling (need munmap on failure)
- Slightly more complex offset calculations

### 4. Eliminating Specialized Kernel Dispatcher Code

**Feasibility: MODERATE**

Currently each specialized kernel contains:
- The actual `ncclDevFunc_*` function
- Helper functions called via PC-relative addressing
- Kernel descriptor (64 bytes)
- Note section (resource usage)

The "dispatcher code" that could be eliminated is the `__device_stub_*` functions generated by HIP, but these are on the host side, not in the device objects. The specialized kernels are pure device code.

What could potentially be eliminated:
- Symbol table entries (currently used for name matching)
- Relocation sections (not used after linking)
- String tables

**Good points:**
- Could reduce per-kernel overhead
- Simplified parsing

**Bad points:**
- Kernel descriptors are required (contain entry point offsets, resource counts)
- Note sections are required (contain VGPR/SGPR/LDS info)
- Would need alternative metadata format

## Speedup Estimate

### Current I/O Profile

- Write 2580 × ~70KB = ~177MB (specialized kernel objects)
- Read 2580 × ~70KB = ~177MB (device linker input)
- Write ~295KB (merged output)
- **Total: ~354MB I/O**

### Estimated I/O Times

| Storage Type | Sequential I/O Speed | I/O Time |
|--------------|---------------------|----------|
| Fast NVMe SSD | 3000 MB/s | ~0.12s |
| SATA SSD | 500 MB/s | ~0.7s |
| HDD | 150 MB/s | ~2.4s |
| NFS (typical) | 50-100 MB/s | ~3.5-7s |
| NFS (congested) | 10-30 MB/s | ~12-35s |

### Additional Overhead Eliminated

- ~5000 syscalls (`open`/`write`/`close` × 2580)
- Filesystem metadata operations
- Buffer cache pressure

### Conservative Speedup Estimate

- Fast local storage: **5-15% improvement** (compilation dominates)
- Network/shared filesystem: **2-5x improvement** (I/O dominates)

## Recommended Implementation Path

Given complexity vs. benefit tradeoffs:

### Phase 1 (Low risk, quick win)

1. Eliminate temp files in `parseKernel()` - use LLVM APIs directly
2. Add mmap'd output option
3. Stream kernel parsing (don't load all into memory first)

**Estimated effort: 1-2 days**

### Phase 2 (Medium complexity)

1. Implement custom in-memory output backend for device linker
2. Pre-compute all offsets before any writes
3. Direct memcpy to mmap'd region

**Estimated effort: 3-5 days**

### Phase 3 (High complexity, optional)

1. Embed Clang for in-memory compilation
2. Requires solving HIP-specific compilation requirements
3. Only worthwhile if Phase 1-2 don't provide sufficient speedup

**Estimated effort: 2-3 weeks**

## Summary

| Aspect | Assessment |
|--------|------------|
| In-memory compilation | Technically feasible but complex; requires embedding libclang |
| Memory buffer reads | Straightforward; device linker already uses LLVM |
| mmap'd output | Straightforward; modest code changes |
| Eliminate dispatcher | Limited benefit; kernels are already minimal |
| **Estimated speedup** | **5-15% (fast SSD) to 2-5x (NFS)** |

The biggest wins come from eliminating the intermediate files when using networked/shared filesystems. On fast local NVMe, the compilation time dominates, so I/O optimization has diminishing returns.
