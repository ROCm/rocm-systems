## Goal
Reduce kernel launch latency by using a "pure specialized kernel approach" with a custom device linker to achieve fast build times.

## Architecture Overview

### The 6 Generic Kernels
Production RCCL has 6 dispatcher kernels (found in `/opt/rocm/lib/librccl.so`):

**Regular (3):**
1. `ncclDevKernel_Generic_1<ncclDevKernelArgsStorage<4096>>`
2. `ncclDevKernel_Generic_2<ncclDevKernelArgsStorage<4096>>`
3. `ncclDevKernel_Generic_4<ncclDevKernelArgsStorage<4096>>`

**Debug (3):**
4. `ncclDevKernelDebug_Generic_1<ncclDevKernelArgsStorage<4096>>`
5. `ncclDevKernelDebug_Generic_2<ncclDevKernelArgsStorage<4096>>`
6. `ncclDevKernelDebug_Generic_4<ncclDevKernelArgsStorage<4096>>`

These are defined in `src/device/common.cu`. They call `ncclKernelMain` which:
1. Calls `loadWorkBatchToShmem()` to load work from kernel args into shared memory
2. Sets `ncclShmem.funcId` from the work batch
3. Dispatches to the appropriate device function

### Dispatch Mechanism

With `USE_INDIRECT_FUNCTION_CALL` defined, dispatch goes through function pointer tables:
```cpp
if (COLL_UNROLL == 1)
    ncclDevFuncTable_1[ncclShmem.funcId]();
else if (COLL_UNROLL == 2)
    ncclDevFuncTable_2[ncclShmem.funcId]();
else
    ncclDevFuncTable_4[ncclShmem.funcId]();
```

Without it, dispatch uses `NCCL_CALL_FUNCTIONS_*` macros (switch/binary search).

### Specialized Device Functions

There are 831 specialized device functions (`ncclDevFunc_*`) for unroll=2 (local GPU only build).
These are generated by `generate_specialized.py` and compiled separately with `-fno-gpu-rdc`.

Each function implements a specific collective operation (e.g., `ncclDevFunc_AllReduce_RING_LL_Sum_f32_0_0_2`).

## Key Technical Constraints

### No `-fgpu-rdc`
The device linker approach requires `-fno-gpu-rdc` (no relocatable device code).
Each compilation unit's device code is self-contained.
This means `extern __device__` symbols cannot be resolved across compilation units at compile time.

### Shared Memory (LDS) Handling

**The Problem:**
- Generic kernels declare `__shared__ ncclShmemData ncclShmem`
- Specialized device functions reference `ncclShmem`
- In non-RDC mode, each compilation unit has its own symbols

**The Solution:**
- LDS is allocated by the kernel at launch time
- All LDS usage starts at offset 0
- Specialized functions have no other LDS declarations - they just access ncclShmem at offset 0
- Generic kernels declare ncclShmem the same way
- When device linker merges the ELFs, all functions access the same LDS layout
- **This already works** - proven by successful tests with one GPU

### Function Pointer Tables

**Current State:**
- `ncclDevFuncTable_1/2/4` are generated in `device_table.h` by `generate.py`
- They are statically initialized with pointers to `ncclDevFunc_*` functions
- This requires all device functions to be in the same compilation unit (RDC mode)

**Device Linker Approach:**
- Function tables should be in `.rodata` (or `.data`)
- Tables are declared/defined in the dispatcher compilation unit
- Device linker populates them with actual function pointers at link time
- The `merged_minimal.hip` file was intended to provide this

## Build Flow

1. **Generate specialized kernels** (`generate_specialized.py`)
   - Creates 831 `.cpp` files, one per device function

2. **Compile specialized kernels** (CMake custom commands)
   - Each compiled with `-fno-gpu-rdc --offload-arch=gfx942`
   - Results in 831 `.o` files with device code in `.hip_fatbin`

3. **Compile dispatcher** (`merged_minimal.hip` or `common.cu`)
   - Contains the 6 generic kernels
   - Contains function table definitions
   - Declares `__shared__ ncclShmemData ncclShmem`

4. **Run device linker** (`device_linker` tool)
   - Extracts device code from all `.o` files
   - Merges into single device ELF
   - Populates function tables with pointers to `ncclDevFunc_*`
   - Outputs merged device image

5. **Build librccl.so**
   - Link host code
   - Inject merged device image into `.hip_fatbin`

## Device Linker Function Table Handling

Looking at `device_linker.cpp`:

1. **Table Creation** (lines 963-965):
   ```cpp
   std::vector<uint64_t> func_table_1(FUNC_COUNT, 0);
   std::vector<uint64_t> func_table_2(FUNC_COUNT, 0);
   std::vector<uint64_t> func_table_4(FUNC_COUNT, 0);
   ```

2. **Table Population** (lines 1005-1018):
   - For each specialized function, device linker extracts `funcId` and `unroll`
   - Stores function's virtual address in the appropriate table slot

3. **Output** (lines 1052-1061):
   - Creates `.data` section with all three tables laid out sequentially
   - Layout: `table_1[859]`, `table_2[859]`, `table_4[859]` (each entry is 8 bytes)
   - Total size: 859 * 8 * 3 = 20,616 bytes

4. **Symbol Relocation** (lines 1080-1095):
   - Device linker fixes `.dynsym` entries that point to the old `.data` range
   - Relocates them to the new merged address

**Key Insight**: The dispatcher (`merged_minimal.hip`) must define the table symbols so:
- The generic kernels can reference them
- The device linker can find and relocate them
- The symbols appear in `.dynsym`

## Open Questions

1. **Function table definition**: 
   - Should be in the dispatcher compilation unit
   - Need symbols in `.dynsym` for device linker to relocate
   - Generic kernels reference these via indirect function call

2. **Guard for dispatch**:
   - The `noinline` guards have pattern: `#if defined(USE_INDIRECT_FUNCTION_CALL) && !defined(__gfx942__) && !defined(__gfx950__)`
   - **On gfx942/gfx950**: `noinline` is ALWAYS used regardless of `USE_INDIRECT_FUNCTION_CALL`
     - Safe to use `USE_INDIRECT_FUNCTION_CALL` - only affects dispatch mechanism
   - **On OTHER architectures**: `USE_INDIRECT_FUNCTION_CALL` REMOVES `noinline`
     - Could cause performance issues (inlining of large functions)
     - Need a separate guard for device linker dispatch
   
   **DECISION: Option B** - Create new `DEVICE_LINKER_DISPATCH` guard
   - Only affects dispatch mechanism in `ncclKernelMain`
   - Does NOT affect `noinline` attributes
   - Keeps existing `USE_INDIRECT_FUNCTION_CALL` behavior unchanged
   - Device linker builds will define `DEVICE_LINKER_DISPATCH` (not `USE_INDIRECT_FUNCTION_CALL`)

3. **Building common.cu with device linker**:
   - Need to compile WITHOUT including `device_table.h` (has static initializers)
   - Need function tables declared as arrays (not `const` with initializers)
   - Need `USE_INDIRECT_FUNCTION_CALL` dispatch behavior

## HIP Compilation Pipeline Analysis

Running `hipcc -###` reveals 4 steps:

### Step 1: Device Compilation
```bash
clang-22 -cc1 -triple amdgcn-amd-amdhsa \
    -fcuda-is-device -target-cpu gfx942 \
    -emit-obj -o /tmp/common-gfx942-XXXXXX.o \
    -x hip common.cu.cpp
```
- Compiles HIP source to device object (relocatable)
- Output: Device `.o` file

### Step 2: Device Linking  
```bash
lld -flavor gnu -m elf64_amdgpu \
    --no-undefined -shared \
    -plugin-opt=-amdgpu-internalize-symbols \
    -plugin-opt=mcpu=gfx942 \
    --whole-archive -o /tmp/common-gfx942-YYYYYY.out \
    /tmp/common-gfx942-XXXXXX.o --no-whole-archive
```
- Links device object into shared ELF (`ET_DYN`)
- Output: Device ELF (`.out`)

### Step 3: Bundle Creation
```bash
clang-offload-bundler -type=o -bundle-align=4096 \
    -targets=host-x86_64-unknown-linux-gnu,hipv4-amdgcn-amd-amdhsa--gfx942 \
    -input=/dev/null \
    -input=/tmp/common-gfx942-YYYYYY.out \
    -output=/tmp/common-ZZZZZZ.hipfb
```
- Bundles null host + device ELF into fatbin
- Output: `.hipfb` bundle

### Step 4: Host Compilation
```bash
clang-22 -cc1 -triple x86_64-unknown-linux-gnu \
    -fcuda-include-gpubinary /tmp/common-ZZZZZZ.hipfb \
    -emit-obj -o skeleton_dispatcher.o \
    -x hip common.cu.cpp
```
- Compiles HIP source for host
- Embeds fatbin into `.hip_fatbin` section
- Output: Final host `.o` with embedded device code

## Device Linker Integration Point

**DECISION: Option B** - Direct fatbin embedding

Pipeline:
1. **Device linker** creates merged device ELF (dispatcher + specialized kernels)
2. **Bundle** merged ELF using `clang-offload-bundler` → `.hipfb`
3. **Host compilation** (step 4 only) with `-fcuda-include-gpubinary merged.hipfb`

This is cleaner than post-compilation replacement because:
- No extraction/replacement of sections
- Single host compilation produces final object
- Easier to integrate into build system

## Production vs Device Linker: Kernel Descriptor Analysis

### Key Finding: How Production Gets KD Values

Production RCCL compiles `common.cu` **together** with all specialized kernels in RDC mode.
This allows the compiler/linker to:
1. Analyze scratch requirements across ALL functions
2. Set `PRIVATE_SEGMENT_FIXED_SIZE` to the **maximum** scratch needed
3. Generate proper scratch initialization code

**Production Generic_2 Kernel Descriptor:**
```
PRIVATE_SEGMENT_FIXED_SIZE: 568 bytes (non-zero - scratch is used)
RSRC2: 0x00000085
  SCRATCH_EN: 1
  USER_SGPR: 2
KERNEL_CODE_PROPERTIES: 0x0008
  enable_sgpr_kernarg_segment_ptr: 1 (only)
```

**Device Linker Generic_2 Kernel Descriptor (original):**
```
PRIVATE_SEGMENT_FIXED_SIZE: 0 bytes (no scratch at compile time!)
RSRC2: 0x00001391
  SCRATCH_EN: 1
  USER_SGPR: 8
KERNEL_CODE_PROPERTIES: 0x081e
  enable_sgpr_dispatch_ptr: 1
  enable_sgpr_queue_ptr: 1
  enable_sgpr_kernarg_segment_ptr: 1
  enable_sgpr_dispatch_id: 1
```

### Root Cause of Multi-GPU Crash

1. **Dispatcher compiled alone** → PRIVATE_SEGMENT_FIXED_SIZE=0
2. **Specialized functions need scratch** → up to 1092 bytes
3. **Device linker updates KD** → PRIVATE_SEGMENT_FIXED_SIZE=1092
4. **But dispatcher CODE wasn't compiled with scratch** → no initialization

When specialized functions do `scratch_store_dword off, v43, s33`:
- They expect s32/s33 to contain valid scratch pointers
- But dispatcher sets `s_mov_b32 s32, 0`
- The runtime allocates scratch (based on patched KD)
- BUT the dispatcher code doesn't properly use it

### Solutions Implemented

1. **Force scratch in dispatcher** (`common.cu`):
   ```cpp
   #ifdef DEVICE_LINKER
   __device__ __noinline__ int ncclDeviceScratchRecurse(int depth, int val) {
     if (depth <= 0) return val;
     volatile int local = val + depth;
     return ncclDeviceScratchRecurse(depth - 1, local);
   }
   __device__ __noinline__ void ncclDeviceScratchReserve() {
     ncclDeviceScratchSink = ncclDeviceScratchRecurse(160, threadIdx.x);
   }
   // Called with unreachable condition in each kernel
   if (ncclDeviceScratchTrigger) ncclDeviceScratchReserve();
   #endif
   ```
   This forces the compiler to recognize scratch usage.

2. **Dynamic s32 patching** (`device_linker.cpp`):
   - Changed from hardcoded offsets to pattern search
   - Finds all `s_mov_b32 s32, 0` (0xBEA00080) and replaces with `s_nop 0`

3. **Disabled RDC linking** for DEVICE_LINKER mode:
   - Removed `-fgpu-rdc` link flag
   - Disabled `hip::device` target (adds `--hip-link`)
   - Our pre-linked device code shouldn't be re-processed

4. **Compile onerank.cu host-only**:
   - Added `--cuda-host-only` flag to prevent conflicting `.hip_fatbin`
   - Without this, linker combines fatbins but only first header is used
   - TODO: Add onerank device code to device linker merge

### Link Order Issue (Resolved)

When linking with multiple `.hip_fatbin` sections:
- Linker concatenates them in order
- Bundle format has single header pointing to first code object
- If onerank.cu.cpp.o comes before dispatcher_final.o, only onerank's device code is recognized

**Fix**: Compile onerank.cu with `--cuda-host-only` so it has no `.hip_fatbin`


**Created `src/device/onerank_stub.cpp`:**
- Provides `ncclLaunchOneRank()` function
- Falls back to simple memcpy instead of kernel-based reduction
- Sufficient for multi-GPU testing (onerank is only for nranks=1 optimization)

This ensures there's only ONE `__hip_fatbin_wrapper` and ONE `__hip_module_ctor`,
avoiding the multi-module registration issues.

### onerank_stub.cpp Explained

The "onerank" optimization is a special case in RCCL where a communicator has only 1 rank 
(single GPU). In this case, collectives like AllReduce are essentially just a memory copy
since there's nothing to reduce across. Production RCCL has a specialized `onerank.cu` 
kernel for this case.

**Why we use a stub instead:**

With the device linker approach, we want a **single fatbin** containing only the dispatcher 
and specialized kernels. Including `onerank.cu` would:
1. Add a separate kernel compilation unit with its own `.hip_fatbin`
2. Create multiple `__hip_fatbin_wrapper` / `__hip_module_ctor` symbols
3. Cause conflicts when the HIP runtime tries to register multiple modules

The stub solution:
```cpp
ncclResult_t ncclLaunchOneRank(void* dst, void const* src, size_t nElts, 
                               struct ncclDevRedOpFull redOp, ncclDataType_t eltType, 
                               hipStream_t stream) {
    // Fall back to hipMemcpyAsync instead of custom kernel
    if (dst != src) {
        size_t eltSize = ncclTypeSize(eltType);
        hipMemcpyAsync(dst, src, nElts * eltSize, hipMemcpyDeviceToDevice, stream);
    }
    return ncclSuccess;
}
```

**Trade-off:** Slightly less optimal for single-rank cases, but:
- Single-rank is rare in real HPC/ML workloads where RCCL is used
- The memcpy fallback is still very fast
- Keeps the device linker build simple with a single fatbin
