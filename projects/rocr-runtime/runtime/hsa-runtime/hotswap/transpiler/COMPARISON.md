# Hotswap Transpiler — Four-Way Comparison

Comparison of all four binary translation prototype approaches: **waveasm**,
**Aster (amdgcn dialect)**, **LLVM MIR**, and **LLVM IR**.

## Pipeline Overview

| Aspect | waveasm | Aster | LLVM MIR | **LLVM IR** |
|--------|---------|-------|----------|-------------|
| **IR Level** | L1 (ISA) | L1.5 (structured ISA) | L1.75 (post-RA MIR) | **L2 (typed SSA)** |
| **Instruction ID** | Mnemonic string | Mnemonic string | Opcode integer | Pattern-match MCInst |
| **Implicit Operands** | Not modeled | Partial (VCC manual) | Automatic (TableGen) | N/A (eliminated) |
| **Register Model** | Precolored virtual regs | Typed physical regs | Physical regs + classes | **Virtual SSA values** |
| **Control Flow** | Linear (no CFG) | Multi-block + VCC branch | Multi-block + exec-mask | **Structured br i1** |
| **Type System** | Untyped | Typed regs only | Register classes | **Full: i32, f32, ptr** |
| **Assembly Gen** | Custom emitter | translateModule | MCInstPrinter | **llc (standard backend)** |
| **Kernel Metadata** | Spliced from original | Manual patching | Manual patching | **Generated by backend** |
| **HSACO Pipeline** | llvm-mc + ld.lld | llvm-mc + ld.lld | llvm-mc + ld.lld | **llc + llvm-mc + ld.lld** |

## Pipeline Results (vecadd, gfx942 same-ISA)

| Metric | waveasm | Aster | LLVM MIR | **LLVM IR** |
|--------|---------|-------|----------|-------------|
| Instructions lifted | 292/292 | 23/23 | 23/23 | 20 matched |
| GPU execution | PASS | PASS | PASS | **PASS** |
| Correct elements | 1024/1024 | 1024/1024 | 1024/1024 | **1024/1024** |
| Manual metadata patching | Yes | Yes | Yes | **No** |
| Output = input bytes | Yes | ~Yes | Yes | **No (recompiled)** |

## The Key Differentiator: Standard Backend Integration

The LLVM IR prototype is the only one where the generated representation
feeds directly into LLVM's standard AMDGPU backend. This means:

1. **No manual kernel descriptor** — `llc` generates `.amdhsa_kernel` with
   correct VGPR/SGPR counts, accum_offset, float modes, etc.
2. **No manual metadata** — `llc` generates the full `.amdgpu_metadata` YAML
   with all hidden argument entries.
3. **Wait counters are recomputed** — `SIInsertWaitcnts` runs automatically,
   producing correct `s_waitcnt` placement for the target.
4. **Register allocation is redone** — the backend picks optimal registers.

Every other prototype must manually construct kernel metadata, which was the
source of multiple bugs and the most fragile part of each pipeline.

## Abstraction Level Comparison

```
waveasm:   s_load_dword s3, s[0:1], 0x2c    (raw instruction, untyped)
Aster:     amdgcn.load(%s0_s1, 0x2c) → %s3   (typed reg, named op)
LLVM MIR:  $sgpr3 = S_LOAD_DWORD_IMM_vi $sgpr0_sgpr1, 44, 0, implicit-def $scc
LLVM IR:   %implicitarg_ptr = call ptr addrspace(4) @llvm.amdgcn.implicitarg.ptr()
           %gsz_ptr = getelementptr i8, ptr addrspace(4) %implicitarg_ptr, i64 12
           %group_size_i16 = load i16, ptr addrspace(4) %gsz_ptr
```

The LLVM IR recovers the **semantic meaning**: this isn't just "load 4 bytes
from offset 44" — it's "read the group size from the implicit argument block."
This semantic recovery enables:
- Retargeting to any ISA (change `-mcpu` flag to `llc`)
- Optimization by standard LLVM passes
- Diffing against compiler output for validation

## When to Choose Each Approach

| Use Case | Best Choice | Reason |
|----------|-------------|--------|
| Quick same-ISA hotswap | waveasm | Simplest, fastest, no analysis |
| Same-vendor cross-ISA | Aster | Instruction-class ops + retarget |
| Analysis (reg pressure, deps) | LLVM MIR | Full implicit operands |
| **Semantic recovery** | **LLVM IR** | **Types, SSA, standard backend** |
| **Cross-ISA via llc** | **LLVM IR** | **Change -mcpu, backend handles rest** |
| **Optimization potential** | **LLVM IR** | **Standard LLVM opt passes** |
| Wide instruction coverage | waveasm | waveasm.raw escape hatch |

## Current State of the LLVM IR Transpiler

The LLVM IR approach has matured into a modular transpiler with broad
instruction coverage:

- **Per-instruction raising**: Every instruction is raised individually via
  format-classified handlers (SOPP, SOP1/2/C/K, VOP1/2/3/3P, SMEM, FLAT,
  MUBUF, DS, MFMA, DPP, VOPD) — 130+ mnemonics and 35+ MFMA shapes
- **Dynamic kernel signatures**: Argument layout is parsed from ELF
  `.amdgpu_metadata` — no hardcoding
- **Cross-ISA transpilation**: gfx1250 (RDNA4) → gfx942 (CDNA3) verified
  end-to-end on hardware (vecadd, softmax, Tensile PostGSU kernels)
- **Scalar EXEC model**: EXEC tracked as a real `i64` alloca with truthful
  save/modify/branch semantics — correct for uniform control flow

See [SHORTCUTS_AND_LIMITATIONS.md](SHORTCUTS_AND_LIMITATIONS.md) for the
full design assessment.

## Architectural Insight

The four prototypes form a spectrum of abstraction vs. generality:

```
Coverage ────────────────────────────────────────── Abstraction
 (wide)                                              (deep)

 waveasm      Aster         LLVM MIR       LLVM IR
 ─────────────────────────────────────────────────▶
 Any kernel   Format-class  All opcodes    Semantic
 Raw bytes    SSA, typed    Implicit ops   Types, SSA
 No analysis  Some analysis Full analysis  Full recovery
 No backend   Partial       Analysis-only  Full backend
```

The recommended production architecture uses **LLVM IR as the target** (for
maximum backend integration) with **MIR as an intermediate** (for instruction
metadata during raising) and **Aster as an alternative codegen path** (for
cases where the full IR raise is not yet possible).
