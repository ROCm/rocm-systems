# LLVM MIR Prototype — Shortcuts and Limitations

Systematic analysis of shortcuts, limitations, and unsound assumptions in the LLVM MIR binary translation prototype.

## Severity Legend
- **HIGH** — Would cause incorrect results or crashes on non-trivial kernels
- **MEDIUM** — Limits applicability but doesn't affect correctness for vecadd
- **LOW** — Engineering debt; straightforward to fix

---

## Lifting (MCInst → MachineInstr)

### 1. ~~No in-process AsmPrinter lowering~~ MachineInstr → MCInst lowering (custom) [RESOLVED → MEDIUM]
~~The MIR → assembly path was intended to use LLVM's AsmPrinter, but `llc` couldn't process our post-RA MIR because the IR function is `declare` (no body).~~

**Resolved**: Assembly is now generated by walking the live `MachineFunction` and lowering each `MachineInstr` back to `MCInst` via explicit operand copying, then printing with `MCInstPrinter`. The MIR **is** in the codegen path — if a `MachineInstr` is modified (opcode, register, etc.), the output assembly reflects the change.

**Remaining gap**: This is a manual lowering, not LLVM's `AsmPrinter`. We don't get late passes (scheduling, `SIInsertWaitcnts`, code alignment) automatically. The lowering handles branch MBB→label resolution but is otherwise a direct operand transcription.

### 2. No liveness tracking [MEDIUM]
We disable `tracksRegLiveness` because we don't compute live-in/live-out sets. This prevents LLVM backend passes (scheduling, spilling) from running correctly on the MIR.

**Impact**: Backend passes that depend on liveness information cannot be used. Register pressure analysis would be unreliable.

### 3. Branch target resolution is offset-based [MEDIUM]
Branch targets are resolved by computing `PC + 4 + simm16 * 4` from the MCInst immediate, then mapping to MBBs. This works for simple forward/backward SOPP branches but:
- Doesn't handle indirect branches or jump tables
- Assumes standard SOPP branch encoding

**Impact**: Only works for simple structured control flow.

### 4. Single-kernel assumption [HIGH]
The lifter assumes the entire `.text` section is a single kernel, stopping at the first `s_endpgm`. Multi-kernel code objects would be truncated.

### 5. s_nop and s_code_end are silently dropped [LOW]
These padding instructions are skipped during lifting. While not semantically important, they affect code alignment and instruction cache behavior.

### 6. MCInst operand count may differ from MCInstrDesc [MEDIUM]
Variadic instructions or instructions with optional operands may have MCInst operand counts that don't match `MCInstrDesc::getNumOperands()`. The current code handles this gracefully for vecadd but may produce incorrect def/use flags for complex instructions.

## Assembly Generation

### 7. ~~MCInstPrinter round-trip instead of AsmPrinter~~ [RESOLVED]
~~The HSACO was generated by re-disassembling the original bytes and printing them as assembly text via `MCInstPrinter`.~~

**Resolved**: Assembly is now generated from the live `MachineFunction` by lowering `MachineInstr` → `MCInst` → `MCInstPrinter`. The original bytes are not re-disassembled for assembly generation. The MIR is the single source of truth for the instruction stream.

### 8. Hardcoded kernel metadata [HIGH]
The kernel descriptor (`.amdhsa_kernel` directives) and YAML metadata are hardcoded for the vecadd kernel:
- `kernarg_size: 288`
- `next_free_vgpr: 8`, `next_free_sgpr: 8`
- Fixed hidden argument layout
- Fixed user SGPR allocation

For any other kernel, these would need to be extracted from the original code object.

### 9. Assembly directives copied from reference [MEDIUM]
The full set of `.amdhsa_*` directives was copied from the original binary's assembly. A production system would need to extract these from the original kernel descriptor.

---

## Pipeline

### 10. External tools dependency [MEDIUM]
Assembly → HSACO uses external `llvm-mc` + `ld.lld` via `std::system()`. Same limitation as the Aster prototype.

### 11. Temporary file I/O [LOW]
Assembly and object files are written to `/tmp/mir_proto.*`. No cleanup, no concurrent execution safety.

### 12. No error recovery [LOW]
If `llvm-mc` or `ld.lld` fails, the pipeline reports failure but doesn't provide detailed diagnostics beyond the exit code.

---

## MIR Quality

### 13. isSSA and noVRegs flags are incorrect [MEDIUM]
The serialized MIR reports `isSSA: true` and `noVRegs: false`, which are defaults for a fresh MachineFunction. Our MIR uses only physical registers and is not in SSA form. These incorrect flags would confuse LLVM passes.

**Fix**: Set `MF.getProperties().set(NoVRegs)` and `MF.setIsSSA(false)`.

### 14. No FrameInfo or stack setup [MEDIUM]
The MachineFunction has default FrameInfo (no stack, no frame pointer). Kernels with stack usage would need proper frame setup.

### 15. MachineFunctionInfo defaults [MEDIUM]
The `SIMachineFunctionInfo` is populated with defaults from the stub IR function. Fields like `explicitKernArgSize: 28` are derived from the function signature, not the original binary.

## Compared to Other Prototypes

### 16. ~~MIR is inspection-only, not in the codegen path~~ [RESOLVED]
~~Unlike waveasm (which emits from its IR) and Aster (which uses translateModule), the LLVM MIR was not connected to the HSACO generation.~~

**Resolved**: The `MachineFunction` is now kept alive in `LiftResult::LiveMF` and `generateAssembly()` walks it to produce the assembly text. The instruction stream in the HSACO comes from the MIR, not the original bytes. Solution #3 (custom `MachineInstr` → `MCInst` lowering) was implemented.

### 17. Cross-ISA translation requires opcode remapping [MEDIUM]
The MIR is now in the codegen path, so cross-ISA translation is architecturally possible by modifying `MachineInstr` opcodes/operands before calling `generateAssembly()`. However, no opcode remapping logic exists yet.

### 18. No wait counter recomputation [MEDIUM]
The MIR is now in the codegen path, making `SIInsertWaitcnts` applicable in principle. However, running LLVM backend passes on the `MachineFunction` requires correct liveness info and MachineFunction properties (see #2, #13) which are not yet set.

## Summary

| Category | Count by Severity |
|----------|-------------------|
| HIGH | 2 (hardcoded metadata, single kernel) |
| MEDIUM | 9 (custom lowering, no liveness, offset-based branches, operand count mismatch, incorrect flags, frame info, func info, external tools, cross-ISA remapping, no waitcnt) |
| LOW | 3 (s_nop dropped, temp files, no error recovery) |
| RESOLVED | 3 (MIR now in codegen path, MCInstPrinter round-trip eliminated, assembly from MIR) |

The prototype successfully demonstrates that:
1. **Implicit operands are free** from `MCInstrDesc` / TableGen
2. **Opcode-based dispatch** works cleanly (no mnemonic parsing for instruction creation)
3. **MIR serialization** produces human-readable output comparable to LLVM test cases
4. **MIR is the source of truth** — assembly is generated by walking the live `MachineFunction`, not by re-encoding the original bytes
5. **MachineInstr modifications are reflected** in the output HSACO
