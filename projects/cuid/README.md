## Introduction
Managing hardware devices (GPUs, CPUs, NICs) in data centers often requires multiple tools, each with its own device identification method. This inconsistency complicates device correlation and management, especially across different vendors. The **Component Unified Identifier (CUID)** solves this by providing a deterministic, unique identifier for each device type, enabling consistent referencing and easier integration.

### What is CUID?

The **Component Unified Identifier (CUID or CUUID)** is generated by combining device-specific data into a 122 bit ID value as follows:

| Bits | Name | Comments |
|------|------|----------|
| 0:63 | Device Serial Number/Fingerprint | from PCIe configuration DSN caps (endpoint), SMBIOS platform serial number, ACPI or other architectural component identifier (if not available, SW generated fingerprint from proprietary individual marker) Integer, may be MSB 0-extended if smaller than 64 bit or truncated if larger |
| 64:71 | UnitID (part 1) | if component supports unitID, 0 otherwise |
| 72:79 | RevisionID | if component supports revision ID, 0 otherwise |
| 80:95 | DeviceID | from PCIe configuration space or SMBIOS ID, For CPU: Family # and Model # values combined |
| 96:111 | VendorID | from PCIe configuration space or SMBIOS vendor ID, follows PCIe vendor ID 16 bit value definition (e.g. 0x1022 or 0x1002 for AMD) |
| 112:116 | UnitID (part 2) | if UnitID value is >= 256, 0 otherwise; UnitID is 13 bits total, split across 64:71 and 112:116 |
| 117 | Auxiliary Value Identifier | 1 when bits 0:63 hold a synthesized auxiliary identity rather than a genuine serial; not part of UnitID; carried unchanged into the derived CUID |
| 118:121 | Component Type | See `amdcuid_device_type_t` in amd_cuid.h, which uses the on-wire values directly |

Component Type uses these values: `0x0` Platform, `0x1` CPU, `0x2` GPU, `0x3` NIC, `0x4` NPU, `0x5` Storage, `0x6` Memory, `0x7` generic PCIe device, `0x8` generic component, `0x9` rack tray, `0xA` rack, `0xB`–`0xE` reserved, `0xF` other. The field spans an octet boundary: its low two bits are the top two bits of payload octet 14, and its high two bits are the low two bits of payload octet 15. A producer that drops payload bits 120:121 therefore renders the type modulo 4 and collides an NPU with a Platform.

`amdcuid_device_type_t` names all sixteen of those values, not only the five this library can discover for itself. A Component Type also arrives from identifiers this library did not produce, such as a kernel-published `cuid_primary` or a record written by another producer, so a Storage or Rack component has to decode to a name rather than to an unnameable integer. `0xB`–`0xE` are reserved and have **no enumerator**. Because the valid range is therefore not contiguous, there is no `AMDCUID_DEVICE_TYPE_LAST` sentinel; it was removed. Test a value with the header-only helper instead:

```c
if (!amdcuid_device_type_is_valid(type)) { /* reserved, or not a Component Type at all */ }
```

`amdcuid_device_type_is_valid()` is true for `0x0`–`0xA` and `0xF`, and false for the reserved `0xB`–`0xE`, for `AMDCUID_DEVICE_TYPE_NONE` (`0xFF`, deliberately outside what a 4-bit field can hold), and for anything else. Widening the enumeration and dropping the sentinel are both ABI breaks, so the library major version is **2** (`AMDCUID_LIB_VERSION_MAJOR`); code that looped to `AMDCUID_DEVICE_TYPE_LAST` must be rewritten against the helper.

This value is then used to fill out a UUIDv8 style format as follows:

| Bit position | Value | Comments |
|--------------|-------|----------|
| 0:47 | ID value (part 1) | LSB of ID value |
| 48:51 | must be 8 (fixed) | for RFC 9562 compliance |
| 52:63 | ID value (part 2) ||
| 64:65 | 10b (fixed) | for RFC 9562 compliance |
| 66:127 | ID value (part 3) | MSB of ID value |

The version and variant bits are **inserted**, not overwritten: they displace the payload after them. The framing preserves payload bits 0 through 121 and discards exactly payload bits 122 through 127, which are always zero, so the payload recovers from the rendered UUID exactly. The bit positions are numbered MSB-first over the rendered octets, so the least significant payload octet appears at the **front** of the printed string: payload `d4abaad39b34c5060000a37302108000` renders as `d4abaad3-9b34-8c50-9800-028dcc084200`.

A **derived CUID** is derived by hashing the primary CUID using HMAC-SHA2-256 (keyed hash) with a 256-bit key. The key is the HMAC key and the 16 packed primary payload octets are the message. The digest folds into the derived payload as `digest[0:63]` → bits 0:63, reserved zero at 64:71, `digest[64:108]` (45 bits) → bits 72:116, bit 117 copied from the primary, reserved zero at 118:121.

Where no genuine serial number is reachable, user-mode software may construct an **auxiliary CUID**: the same layout, the same Component Type numbering, the same UUIDv8 framing and the same derivation, distinguished solely by bit 117 being set. The version nibble is always `8`; a consumer tests bit 117 rather than branching on the UUID version. This obscures hardware details from lower-privilege software and prevents precomputed table attacks.

An auxiliary CUID is built by the device class that can build one, out of attributes that actually name the device. When even that is impossible, whether from no serial, no usable attributes, or no machine identity on the host (`/etc/machine-id`, falling back to `/var/lib/dbus/machine-id`), the library **returns an error**. It does not synthesise a placeholder. It used to: a device whose primary lookup failed was given an all-zero payload with the auxiliary bit set, so every such device on every machine HMACed the same octets under the same fixed public key and collided on one identifier, while the caller was told the value was unique. The machine-identity case is the same failure at host granularity: with the Machine ID field zeroed the auxiliary input reduces to properties of the hardware model and its slot, so two identically-configured hosts would emit the same auxiliary CUID for different physical parts. The kernel takes the same position: with no serial it publishes nothing. Callers must handle the error rather than assume an identifier always comes back. To protect the serial number with sensitive information, users of the tool must provide the 256-bit key to use for the keyed hashing function, as described in FIPS 198-1, The Keyed-Hash Message Authentication Code (HMAC). This key must be unique, random, and protected from unauthorized use. This scheme will result in additional management overhead to securely store the key. The key should only be accessible to privileged users or the privileged service who would then use the key along with the primary ID in the HMAC-SHA2-256 function to generate the derived ID.

### CUID File

Privileged applications generate and share derived CUIDs with non-privileged users via a file (the **CUID file**) or IPC. It is updated by a daemon, boot script, or cron job.

The record store is `/var/lib/amdcuid/`: `/var/lib/amdcuid/cuid` holds the world-readable records, and `/var/lib/amdcuid/priv_cuid` the privileged ones. The directory is root-owned and mode `0755`; the privileged record is not world-readable.

> **Security note.** These files were previously `/tmp/cuid` and `/tmp/priv_cuid`. A world-writable directory is not a safe place for a file a root-privileged refresh writes and every consumer trusts: any local user could pre-create the path, or the predictable temporary file beside it, and steer a root write. That was a local privilege-escalation defect and the move to `/var/lib/amdcuid` is its fix. Do not configure the store back under `/tmp`.

`AMDCUID_RECORD_DIR` overrides the directory, and is honoured **only for a non-root caller**. An ordinary user redirecting its own store somewhere it can actually write is harmless, and is how a test (or a caller on a node where no privileged refresh has ever run) gets a store at all. For an effective UID of 0 the variable is ignored outright, because letting the environment steer where a root-privileged refresh writes primary CUIDs and hardware fingerprints would reopen exactly the hole the move closed. The compiled-in default can also be changed at build time with `-DAMDCUID_RECORD_DIR=...`, which is the supported way for packaging to relocate the store.

#### Example CUID File Format

```ini
[GPU:0]
derived_cuid=XXXXXXXX-XXXX-XXXX-XXXX-XXXXXXXXXXXX
vendor_id=1022
device_id=1974
pci_class=0004
revision_id=01
unit_id=0002
device_node=/sys/class/drm/renderD128
last_update=1753987166

[CPU:0]
derived_cuid=XXXXXXXX-XXXX-XXXX-XXXX-XXXXXXXXXXXX
vendor_id=1022
device_id=1974
revision_id=01
family=0019
model=0074
unit_id=0004
package_id=0
last_update=6980d761

[NIC:0]
derived_cuid=XXXXXXXX-XXXX-XXXX-XXXX-XXXXXXXXXXXX
vendor_id=1414
device_id=0003
pci_class=0005
revision_id=10
device_node=/sys/class/net/enp131s0
last_update=1753987166

[PLATFORM]
derived_cuid=XXXXXXXX-XXXX-XXXX-XXXX-XXXXXXXXXXXX
vendor_id=1573
last_update=1753987166
```

- **GPU:** `device_node` links the CUID to hardware.
- **CPU:** `package_id` identifies physical CPU package, akin to the socket.
- **NIC:** `device_node` links to the network device.
- **PLATFORM:** Only the derived CUID is listed.

`last_update` is a Unix timestamp for the last modification.

#### Including Primary CUID (Privileged Users)

Privileged users can map `primary_cuid` to `derived_cuid`:

```ini
[GPU:0]
primary_cuid=YYYYYYYY-YYYY-YYYY-YYYY-YYYYYYYYYYYY
derived_cuid=XXXXXXXX-XXXX-XXXX-XXXX-XXXXXXXXXXXX
hardware_fingerprint=ZZZZZZZZ
vendor_id=1022
device_id=1974
pci_class=0004
revision_id=01
unit_id=0002
device_node=/sys/class/drm/renderD128
last_update=1753987166
```

> **Note:** The file contains sensitive information. Restrict access to `primary_cuid`.

### CUID Tool Overview

The CUID tool supports both privileged and non-privileged users:

#### CUID Library

- Discovers hardware and constructs primary CUIDs.
- Generates derived CUIDs via hashing.
- Provides APIs for device info and identifiers.

##### Re-keying

`amdcuid_set_hash_key()` is an administrative invalidation of every derived CUID already handed out, not a routine call. It does three things, in this order:

1. writes the new 256-bit key to the key file and to the in-memory key object;
2. writes the same 32 octets to each discovered PCI device's sysfs `cuid_seed`, so the driver recomputes its published `cuid_secondary`;
3. drops the recorded derived values and rebuilds them under the new key.

Step 2 is what makes a re-key actually take effect. Derivation prefers the driver's published `cuid_secondary` over anything this library computes, so replacing only the key file and the records left every GPU whose driver publishes the attribute still serving its pre-re-key value, the one outcome a re-key exists to prevent. The write is exactly 32 raw bytes: the kernel rejects any other length.

A device with no `cuid_seed` attribute is not a failure: there is no driver-published value to go stale. A device that has the attribute and refuses the write is a failure, and `amdcuid_set_hash_key()` returns `AMDCUID_STATUS_PERMISSION_DENIED` or `AMDCUID_STATUS_FILE_ERROR` in that case, meaning "the node is re-keyed, and these devices are still serving the old value".

#### Command Line Interface (CLI)

- Uses the library to detect devices and generate CUIDs.
- Allows creation of primary/derived CUIDs (if privileged).
- Simplifies device management and integration.

### Build and Install Instructions

The below instructions allow the building of the CUID project and also the installation of its files and services:

```sh
mkdir build
cd build
# Set CMAKE_INSTALL_PREFIX as needed (default is typically /opt/rocm/core)
# Add -DBUILD_DAEMON=ON to also build the daemon (optional)
cmake -DCMAKE_INSTALL_PREFIX=/opt/rocm ..
make
# Use sudo if installing to a system prefix like /opt
sudo make install
# Replace <install-prefix> with the value used for CMAKE_INSTALL_PREFIX above
sudo <install-prefix>/share/amdcuid/amdcuid_postinst.sh
```

Both static and shared libraries are built. The post-install script is a unified entry point: it always provisions the HMAC key required by the library, and automatically configures the `systemd` service and `udev` rules if the daemon was also installed.

If users need to uninstall the CUID project, they can do so with the following instructions:

```sh
cd build
# Replace <install-prefix> with the value used for CMAKE_INSTALL_PREFIX above
sudo <install-prefix>/share/amdcuid/amdcuid_prerm.sh
sudo make uninstall
```

The pre-removal script automatically stops and removes the `systemd` service and `udev` rules if the daemon is installed, and skips those steps otherwise. The HMAC key and daemon config in `/etc/amdcuid/` are intentionally preserved so that reinstalls keep the same CUID values. To fully purge all configuration, run `sudo rm -rf /etc/amdcuid` after uninstalling.

Documentation can be built using the following instructions:

```sh
pip install -r docs/sphinx/requirements.txt
sphinx-build docs docs/_build/html
```

#### Notes

- No third-party crypto dependency: SHA-256 and HMAC-SHA-256 are built from source out of the shared `shared/sha256` component, whose objects are absorbed into `libamdcuid_static.a`, so the shipped archive is self-contained and the library links no TLS stack on any platform
- Root/administrator privileges are required for full functionality (ACPI tables, SMBIOS UUID, PCI config space access)
- systemd is only needed for `udevd` reloads and optional service management; the daemon can also be started using other mechanisms such as an `@reboot` cron job
