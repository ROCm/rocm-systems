## Purpose

The DerivedID: the keyed-hash value privileged software produces from a
PrimaryID and hands to lower-privilege software, and the shared secret it is
keyed with.

_Source: "Persistent platform component identification for SW tools", version 84._

## Requirements

### Requirement: Derivation by HMAC-SHA-256

The DerivedID SHALL be produced by an HMAC algorithm over two inputs:

- the **message**: the PrimaryID's 122-bit value, LSB first;
- the **key**: a 256-bit shared "salt", established across the cloud nodes,
  whose persistence is what makes the DerivedID persistent.

The hash function SHALL be SHA2-256.

> **Recorded gap (C2).** The message is given as "the primary ID 122bit wide
> value as LSB". HMAC-SHA-256 consumes octets, and 122 bits is not a whole
> number of octets. The page never says how the 122 bits are presented to the
> algorithm: as 16 octets with six zero pad bits, or otherwise. Two producers
> can differ here and both claim conformance, and the resulting values share no
> bits. Resolved in `openspec/changes/amend-published-cuid-spec/`.

#### Scenario: The operands

- **WHEN** a DerivedID is generated
- **THEN** the PrimaryID payload is the message and the shared salt is the key

#### Scenario: The salt is 256 bits

- **WHEN** the shared secret is established
- **THEN** it is 256 bits

#### Scenario: A shared salt gives a shared answer

- **WHEN** two nodes carrying the same salt derive from the same PrimaryID
- **THEN** they produce the same DerivedID

### Requirement: Derived payload layout

The 122 bits of the DerivedID value SHALL be laid out as:

| Bit | Name | Comments |
|---|---|---|
| 0:63 | bits [0:63], LSB of hash value | Generated from the Primary CUID |
| 64:71 | Reserved | Must be 0 |
| 72:116 | bits [64:109], MSB of hash value | Generated from the Primary CUID |
| 117 | Auxiliary Value Identifier | Indicates the value represents a manufactured ID, where the primary CUID is not canonically generated |
| 118:121 | Reserved2 | Must be 0 |

The structure allows the UnitID field to be masked where that is appropriate for
the handling of the CUID, without requiring a specific distinction.

> **Recorded contradiction (C11, width).** The slot at 72:116 is 45 bits, but is
> labelled `bits [64:109]`, which is 46 bits. The two cannot both hold.
>
> **Recorded contradiction (C11, prose).** The surrounding prose states that "the
> DerivedID uses the 110 bit LSB of the resulting hash alongside with 12 bits
> reserved". The table carries 64 + 45 = 109 hash bits and 13 reserved or
> flag bits. The prose and the table disagree by one bit in each direction.
>
> **Recorded contradiction (C10, bit 117).** `primary-identifier` assigns bit 117 to
> UnitID part 2. This table assigns it to the Auxiliary Value Identifier.
>
> All three are resolved in `openspec/changes/amend-published-cuid-spec/`.

#### Scenario: The reserved fields are zero

- **WHEN** a DerivedID payload is decoded
- **THEN** bits 64:71 and 118:121 are zero

> **Recorded contradiction (C7).** The stated figure assumes "the DerivedID is
> built from 122 custom bits of the hash value". The table above carries at most
> 109 hash bits; the other 13 are reserved or the auxiliary flag, and are fixed.
> The collision bound follows from the number of *varying* bits, so the figure
> is overstated by 13 bits. Resolved in
> `openspec/changes/amend-published-cuid-spec/`.

#### Scenario: Collision resistance

- **WHEN** the chance of an accidental collision is computed
- **THEN** the specification states 1/(2^(122-1))

### Requirement: Generation time and lifetime

The DerivedID SHALL be generated by system software from the current PrimaryID
when the first context on the underlying device is created, and SHALL be
persistent for the lifetime of the software context it is defined in, whether a
process, a container or a VM.

#### Scenario: First context creation

- **WHEN** the first lower-privilege context on a device is created
- **THEN** the DerivedID is generated at that point

### Requirement: Out-of-band regeneration

For out-of-band use of a DerivedID in pre-OS scenarios, the same algorithm
SHOULD be used to regenerate the authentication code, either by initiating the
key exchange from the tool level, or by persisting the salt in platform secure
storage (for example through UEFI mechanisms) and retrieving it under
appropriate authentication for administrator-level tools.

The mechanisms for securely storing the authentication code are defined in other
standards (Trusted Computing Group, UEFI Forum). The management processes for
storage and retrieval MAY be deployment specific, and are outside the scope of
this specification provided the value can be made available.

That proviso is a condition, not an aside. Where out-of-band regeneration is
required, the deployment SHALL make the same salt retrievable by the
out-of-band consumer, whichever mechanism it chooses.

#### Scenario: A device moved between systems

- **WHEN** a component is physically moved to another system in the same
  deployment
- **THEN** its DerivedID can be regenerated there, because the salt is shared
  across the deployment
