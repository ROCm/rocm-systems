=======================
IO backend architecture
=======================

hipFile uses a two-backend design for every read and write operation. At IO submission time, the library evaluates each backend's willingness to service the request and dispatches work to the most suitable one. If the preferred backend encounters a transient error, the request can be retried automatically on the other backend. This page describes both backends, the scoring model that selects between them, and the environment variables that control fallback behavior.

   flowchart LR

       B --> C{"Fastpath score >= 0?"}

       C -- No --> F["Fallback IO\n(pread/pwrite + hipMemcpy)"]
       D -- "ENODEV / EREMOTEIO" --> F

Fastpath backend
****************

The fastpath backend transfers data directly between storage and GPU memory through the HIP runtime, the ROCR runtime, HSA, and the KFD kernel driver. Because the kernel driver performs DMA on behalf of the GPU, no CPU staging buffer is involved and the data does not pass through the kernel page cache.

Requirements
------------

The fastpath backend's ``score()`` function checks a set of preconditions before accepting a request. If any check fails, the function returns a negative score (refusing the request). The checks include:

File descriptor
   The file must have been opened with ``O_DIRECT``. hipFile internally maintains both a buffered and an unbuffered file descriptor for each registered file and uses the unbuffered descriptor for fastpath IO. If no unbuffered descriptor is available, the fastpath refuses the request.

Memory type
   The destination or source buffer must be ``hipMemoryTypeDevice`` memory. Only device-resident buffers can participate in the direct DMA path.

Filesystem
   The file must reside on a block device, or on a regular file stored on an **ext4** filesystem with ordered journaling mode, or on an **xfs** filesystem. Files on other filesystems are rejected by the fastpath unless the ``HIPFILE_UNSUPPORTED_FILE_SYSTEMS`` environment variable is set to ``true``.

Alignment
   File offsets, buffer offsets, and IO sizes must be aligned to the filesystem's direct IO alignment. hipFile queries this alignment from ``statx`` using ``STATX_DIOALIGN``; if the information is not available, it defaults to **4096 bytes**. The ``BLOCK_ALIGN`` constant used in the example programs is likewise defined as ``4096``.

IO size limit
   A single IO operation transfers at most ``0x7ffff000`` (2,147,479,552) bytes, matching the Linux kernel's ``MAX_RW_COUNT`` limit. ``getMaxRwCount()`` in the library computes this value as ``INT_MAX & ~(page_size - 1)``. Larger requests are capped to this size. The ``aiscp`` example defines ``AISCP_CHUNK_SIZE`` to the same value and loops over multiple calls for files that exceed it.

Fallback backend
****************

The fallback backend uses POSIX ``pread`` and ``pwrite`` system calls combined with ``hipMemcpy`` to bounce data through a host-memory buffer. Because it does not require ``O_DIRECT``, specific filesystem types, or aligned offsets, it can service any IO request that the fastpath cannot.

For synchronous IO, the fallback performs:

1. A ``pread`` or ``pwrite`` between the file and a host bounce buffer.
2. A ``hipMemcpy`` between the host bounce buffer and the GPU device buffer.

For asynchronous IO, the fallback path uses ``hipLaunchHostFunc`` and the ``hipFileMemcpyKernel`` HIP kernel to interleave CPU-side IO and GPU memory copies on the stream, so that work proceeds without blocking the calling thread.

Backend scoring model
*********************

Each backend implements a ``score()`` method that returns an integer:

- A **negative** return value means the backend refuses the request.
- A **non-negative** return value means the backend is willing. Higher values indicate greater eagerness.

When hipFile dispatches an IO operation, it queries every registered backend and selects the one with the highest non-negative score. In practice, the fastpath returns a positive score when all of its preconditions are met and a negative score otherwise. The fallback backend accepts any request, so it acts as the catch-all.

Automatic fallback with ``BackendWithFallback``
***********************************************

The fastpath backend extends ``BackendWithFallback``, a wrapper that intercepts errors from a primary backend and optionally retries the IO on a registered fallback backend. After the primary backend's ``_io_impl`` returns or throws, ``BackendWithFallback`` calls ``is_fallback_eligible()`` to decide whether to retry:

- If the primary backend reports ``ENODEV`` or ``EREMOTEIO``, the request is eligible for automatic fallback.
- If fallback is eligible and a fallback backend has been registered (via ``register_fallback_backend``), the request is resubmitted to that backend transparently.

This means that a request can initially target the fastpath and still complete through the POSIX path without the caller needing to handle the retry.

Compatibility mode controls
***************************

Two environment variables govern whether the fallback path is available:

``HIPFILE_ALLOW_COMPAT_MODE``
   Controls whether IO operations can fall back to the POSIX path when the fastpath cannot complete them. When set to ``true`` (the default behavior), fallback is permitted. When set to ``false``, operations that cannot be completed by the fastpath are rejected. The ``no-odirect-write`` example demonstrates this variable: it opens a file without ``O_DIRECT`` and requires ``HIPFILE_ALLOW_COMPAT_MODE=1`` to succeed.

``HIPFILE_FORCE_COMPAT_MODE``
   When set to ``true``, the fastpath is disabled entirely and all IO is routed through the POSIX fallback path. When set to ``false`` (the default behavior), the fastpath is used when its preconditions are met.

These variables are read from the process environment at library initialization through the ``Environment`` class and are reflected in the ``Configuration`` class methods ``fastpath()`` and ``fallback()``.

For a full list of environment variables and their accepted values, see :doc:`/conceptual/environment-variables`. For details on driver initialization and the reference-counted lifecycle, see :doc:`/reference/api-driver-lifecycle`.
