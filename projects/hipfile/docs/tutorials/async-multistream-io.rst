=============================================
Async multi-stream IO with registered streams
=============================================

This tutorial walks through a complete round-trip example that reads a file into
GPU memory and writes it back out, splitting the work across multiple HIP
streams running concurrently. Each stream is registered with hipFile using
optimization hints so the driver can skip per-submission validation. The
example is based on ``examples/async/roundtrip-async-multi-stream-registered.cpp``
in the hipFile source tree.

.. warning::

   Asynchronous IO is not yet supported on AMD backends in the current
   release. The APIs are available and compile, but calls return
   ``hipFileAsyncNotSupported`` on AMD ROCm platforms. The workflow described
   here functions on NVIDIA platforms via the cuFile backend.

When to use this pattern
************************

Use multi-stream registered async IO when you need to:

- Transfer large files in parallel slices, keeping the GPU busy with
  overlapping reads and writes.
- Reduce per-submission overhead by declaring fixed buffer offsets, file
  offsets, file sizes, and page-aligned inputs at stream registration time.
- Pipeline storage IO with GPU compute on separate streams.

Prerequisites
*************

- A working hipFile installation (see :doc:`/install/install`).
- An AMD or NVIDIA GPU with hipFile support.
- A filesystem that supports ``O_DIRECT`` (for example, ext4 or XFS).
- The ``examples_common`` helper library shipped with hipFile
  (``examples/common/``).

Complete source code
********************

The full example is reproduced below. The sections that follow explain each
logical step.

Step-by-step walkthrough
************************

Select the GPU and seed the input file
--------------------------------------

.. code-block:: cpp

   hip_err = hipSetDevice(gpu_id);

   if (seed_read_file(read_path, TOTAL_SIZE))
       return EXIT_FAILURE;

``seed_read_file`` creates a file filled with a deterministic byte pattern
(``byte i = i & 0xFF``) using plain POSIX IO. The total size is
``NUM_STREAMS * SLICE_SIZE`` — by default, 4 × 1 MiB = 4 MiB.

Allocate per-stream GPU buffers and register them
-------------------------------------------------

For each of the ``NUM_STREAMS`` streams, the example allocates a GPU buffer
with ``hipMalloc``, registers it with hipFile, creates a non-blocking HIP
stream, zeros the buffer on that stream, and then registers the stream with
the driver.

Key points:

- Each buffer is registered separately with ``hipFileBufRegister``. The
  ``flags`` argument is ``0``.
- Streams are created with ``hipStreamNonBlocking`` so they do not
  implicitly synchronize with the legacy default stream.
- ``hipFileStreamRegister`` accepts a combination of flags that tell the
  driver what properties are fixed for all future submissions on this stream:

  ``HIPFILE_STREAM_FIXED_BUF_OFFSET``
      Buffer offset does not change between submissions.

  ``HIPFILE_STREAM_FIXED_FILE_OFFSET``
      File offset does not change between submissions.

  ``HIPFILE_STREAM_FIXED_FILE_SIZE``
      Transfer size does not change between submissions.

  ``HIPFILE_STREAM_PAGE_ALIGNED_INPUTS``
      All offsets and sizes are 4 KiB aligned.

  These hints let the driver skip per-submission validation, reducing
  overhead for high-frequency async IO.

- The ``slice_state`` struct stores sizes and offsets as named fields because
  the async API takes these parameters **by pointer** and dereferences them
  at completion time. They must remain valid until ``hipStreamSynchronize``
  completes.

Open input and output files
---------------------------

Both files are opened with ``O_DIRECT`` so hipFile can use its direct GPU
IO fast path. The helper ``open_file`` (from ``examples_common``) calls
``open(2)`` followed by ``hipFileHandleRegister``. A single pair of file
descriptors is shared across all streams.

Submit reads on all streams
---------------------------

Each call to ``hipFileReadAsync`` enqueues a read of ``SLICE_SIZE`` bytes at
file offset ``i * SLICE_SIZE`` into the corresponding GPU buffer. Because the
streams are independent, these reads can execute concurrently.

Submit writes on all streams
----------------------------

Each write is submitted on the **same stream** as the corresponding read.
HIP stream semantics dictate that operations on a single stream execute in
submission order. This means the write for slice *i* observes the completion
of the read for slice *i* without requiring an explicit synchronization call
between the two. Across different streams, reads and writes can overlap
freely.

Synchronize and verify byte counts
----------------------------------

After synchronization, the ``bytes_read`` and ``bytes_written`` fields in
each ``slice_state`` contain the actual transfer counts. The example checks
that every slice transferred the full ``SLICE_SIZE``.

Hash-verify the output file
---------------------------

``verify_files_match`` hashes the first ``TOTAL_SIZE`` bytes of both files
using FNV-1a and compares the results. A match confirms the round trip was
lossless.

Clean up resources
------------------

Teardown follows the reverse of setup order for each slice:

1. ``hipFileStreamDeregister`` — deregister the stream from hipFile.
2. ``hipStreamDestroy`` — destroy the HIP stream.
3. ``hipFileBufDeregister`` — deregister the GPU buffer from hipFile.
4. ``hipFree`` — free the GPU memory.

The per-entry boolean flags (``stream_registered``, ``stream_created``,
``buf_registered``) handle partial setup gracefully — if setup fails midway
through the loop, only the resources that were successfully created are
released.

Stream ordering
***************

The correctness of this example relies on HIP stream ordering:

- Within a single stream, operations execute in submission order. The
  ``hipFileWriteAsync`` for slice *i* is submitted after
  ``hipFileReadAsync`` for the same slice on the same stream, so the write
  observes the completed read without extra synchronization.
- Across different streams (``hipStreamNonBlocking``), there is no ordering
  relationship. Slices can read and write in parallel.

This pattern scales naturally: increasing ``NUM_STREAMS`` adds more
concurrent slices. Each stream operates on a non-overlapping region of
the file, so no inter-stream coordination is needed.

Running the example
*******************

.. code-block:: console

   $ ./roundtrip-async-multi-stream-registered /path/to/readfile /path/to/writefile [GPUID]

On success, the program prints:

.. code-block:: text

   OK  /path/to/readfile == /path/to/writefile  (4194304 bytes across 4 registered streams, hash 0x...)
