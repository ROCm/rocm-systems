*********************************
Registration and driver lifecycle
*********************************

hipFile organizes its state into three registration levels: the **driver**
(library singleton), **file handles**, and **GPU memory buffers**. Understanding
how these levels interact — especially the implicit initialization behavior and
the reference-counting rules — is important for writing correct teardown logic.

.. mermaid::

   flowchart LR
     A["hipFileDriverOpen"] --> B["Driver initialized\n(refcount incremented)"]
     C["hipFileHandleRegister"] --> D{"Driver open?"}
     E["hipFileBufRegister"] --> D
     D -- No --> B
     D -- Yes --> F["Register resource"]
     B --> F
     F --> G["hipFileDriverClose\n(refcount decremented)"]

Driver reference counting
*************************

The hipFile driver is a process-level singleton. Its state is managed by a
reference count:

- Each call to ``hipFileDriverOpen`` increments the count. If the count
  transitions from zero to one, the library's internal state is initialized.
- Each call to ``hipFileDriverClose`` decrements the count. If the count
  transitions from one to zero, all library state — file registrations, buffer
  registrations, and streams — is cleaned up.

You can query the current reference count at any time with ``hipFileUseCount``.

Explicitly closing the library is not required; its state is destroyed
automatically at program exit.

For the full driver API reference, see
:doc:`/reference/api-driver`.

Auto-initialization
-------------------

Calling ``hipFileDriverOpen`` before any other hipFile call is optional.
The first call to either ``hipFileHandleRegister`` or ``hipFileBufRegister``
initializes the driver and increments the reference count if the driver has
not been opened yet. This implicit open is convenient, but it has an
important consequence: the implicit open is not tracked separately, so you
must account for it when balancing ``hipFileDriverClose`` calls. If your
intent is to fully shut down the driver, check ``hipFileUseCount`` rather
than relying solely on matching open and close calls.

These auto-initialization calls increment the driver count only when they
succeed.

File handle registration
************************

Before performing any IO on a file, you must register it with hipFile via
``hipFileHandleRegister``. The function accepts a ``hipFileDescr_t`` that
specifies the handle type (``hipFileHandleTypeOpaqueFD`` for a POSIX file
descriptor, ``hipFileHandleTypeOpaqueWin32`` for a Win32 handle, or
``hipFileHandleTypeUserspaceFS`` for a userspace RDMA filesystem) and
returns an opaque ``hipFileHandle_t``.

Dual file descriptors
---------------------

When a file is registered, hipFile internally inspects the supplied file
descriptor and maintains up to two descriptors for it:

- A **buffered** file descriptor (without ``O_DIRECT``).
- An **unbuffered** file descriptor (with ``O_DIRECT``), opened automatically
  via ``/proc/self/fd`` if the original descriptor does not already carry
  ``O_DIRECT``.

The buffered descriptor is used by the POSIX fallback path, while the
unbuffered descriptor is required by the fastpath backend. If the file does
not support direct IO, the unbuffered descriptor might not be available and
the fastpath will decline the request. For more detail on backend selection,
see :doc:`/conceptual/io-backends`.

Registration also collects filesystem metadata — ``statx`` attributes,
``/proc/self/mountinfo`` data, and direct-IO alignment values
(``m_dio_mem_align``, ``m_dio_offset_align``) — that the backends consult
when scoring an IO request. If alignment information is not available from
``statx``, both values default to 4096 bytes.

When you are finished with a file, call ``hipFileHandleDeregister`` to
release the associated resources.

For the complete file handle and buffer API reference, see
:doc:`/reference/api-file-and-buffer`.

Buffer registration
*******************

GPU memory buffers used with hipFile should be registered with
``hipFileBufRegister`` before IO. Registration tells the library to track
the buffer internally so it can be used directly on the fastpath without
intermediate copies.

Registered versus unregistered buffers
--------------------------------------

When you pass a **registered** buffer to ``hipFileRead`` or
``hipFileWrite``, hipFile uses the buffer directly for the IO transfer.
This is the recommended path for performance-sensitive workloads.

When you pass an **unregistered** buffer, hipFile routes the transfer
through an internal temporary pool (bounce buffer). IO still completes
correctly, but the extra copy through the bounce pool might reduce
throughput compared to using a registered buffer. The
``no-bufregister-write`` example in the hipFile source tree demonstrates
this path.

Only device memory (``hipMemoryTypeDevice``) can be registered. Managed
memory and pinned host memory are accepted by the IO functions but are
not registered via ``hipFileBufRegister``; instead, hipFile handles them
through alternative internal paths.

When a buffer is no longer needed for IO, deregister it with
``hipFileBufDeregister``.

Matching registration and deregistration
****************************************

A well-structured hipFile program follows a consistent teardown order.
The example programs in the hipFile source tree demonstrate a pattern
where cleanup unwinds in reverse order of setup:

1. Deregister streams (if using async IO).
2. Destroy HIP streams.
3. Deregister file handles (``hipFileHandleDeregister``).
4. Close POSIX file descriptors.
5. Deregister buffers (``hipFileBufDeregister``).
6. Free GPU memory (``hipFree``).
7. Close the driver (``hipFileDriverClose``), checking
   ``hipFileUseCount`` if full shutdown is required.

Because ``hipFileHandleRegister`` and ``hipFileBufRegister`` can each
implicitly bump the driver reference count, the total number of
``hipFileDriverClose`` calls needed might exceed the number of explicit
``hipFileDriverOpen`` calls. Query ``hipFileUseCount`` to confirm the
count has reached zero if you need deterministic cleanup.
