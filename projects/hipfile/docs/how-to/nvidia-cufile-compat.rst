==============================================
Use hipFile with NVIDIA (cuFile compatibility)
==============================================

hipFile supports NVIDIA platforms by delegating IO operations to the cuFile library. This page explains how to configure the build for an NVIDIA target and documents the known behavioral differences between the hipFile API and cuFile.

For general installation instructions, see :doc:`/install/install`.

Build for NVIDIA
****************

To compile hipFile for an NVIDIA platform, set ``CMAKE_HIP_PLATFORM`` to ``nvidia`` so the build system selects the NVIDIA detail layer instead of the AMD detail layer. The build requires:

- An NVIDIA CUDA Toolkit installation (CMake locates it through the ``CUDAToolkit`` package).
- The cuFile library, which ships with the CUDA Toolkit in supported configurations.

.. code-block:: shell

   cmake -B build \
       -DCMAKE_HIP_PLATFORM=nvidia \
       ..
   cmake --build build -j

When ``CMAKE_HIP_PLATFORM=nvidia`` is set, the hipFile library links against cuFile and forwards every hipFile API call to the corresponding cuFile entry point at runtime.

Known differences from cuFile
*****************************

hipFile strives for a 1:1 correspondence with the cuFile API surface so that porting code is straightforward. Several differences exist, however, and code that relies on undocumented cuFile behavior might need adjustment.

Error code values
-----------------

Specific numeric error code values might differ between cuFile and hipFile. They might also change across hipFile releases. Robust error handling should check for any error first and then optionally drill down into specifics. See :doc:`/reference/api-errors` for recommended patterns.

``hipFileDriverOpen``, ``hipFileDriverClose``, and ``hipFileUseCount`` semantics
--------------------------------------------------------------------------------

The side effects of ``hipFileDriverOpen()``, ``hipFileDriverClose()``, and the use count reported by ``hipFileUseCount()`` might not match cuFile's behavior. A special driver-initialization API call might not remain necessary in future hipFile releases. For more detail on the driver lifecycle, see :doc:`/reference/api-driver`.

``hoff_t`` instead of ``off_t``
-------------------------------

hipFile uses a platform-independent ``hoff_t`` type in place of ``off_t``. On POSIX systems ``hoff_t`` is defined as ``off_t``; on Windows it is defined as ``__int64``. This avoids the 32-bit ``off_t`` problem that exists on some Windows configurations.

No ``cuFileDriverClose_v2`` alias
---------------------------------

cuFile's header contains ``#define cuFileDriverClose cuFileDriverClose_v2``. hipFile has no equivalent; both the v1 and v2 cuFile symbols map to ``hipFileDriverClose()``.

No ``sockaddr_t`` typedef
-------------------------

``hipfile.h`` does not typedef ``struct sockaddr`` to ``sockaddr_t`` as ``cufile.h`` does. Code that references ``sockaddr_t`` should use ``struct sockaddr`` directly or add its own typedef.

HIPIFY tool support
*******************

The ``amd-develop`` branch of `ROCm/HIPIFY <https://github.com/ROCm/HIPIFY>`_ includes support for converting cuFile API calls to hipFile API calls. A cuFile-to-hipFile API map is available in the `HIPIFY reference tables <https://github.com/ROCm/HIPIFY/blob/amd-develop/docs/reference/tables/cuFile_API_supported_by_HIP.md>`_.

.. note::

   The hipFile changes in HIPIFY are not yet included in a public release. Use the ``amd-develop`` branch to access them.
