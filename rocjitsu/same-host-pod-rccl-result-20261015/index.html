    Same-host pod RCCL qualification, 2026-10-15¶

    The same-host gate passed in QEMU/VFIO and emulated KFD modes. Four independent nodes ran on one physical host. Each node contained two modeled gfx1250 A0 GPUs, and each GPU ran one RCCL rank in the same eight-rank communicator. Local GPU traffic traversed modeled node-local Infinity Fabric endpoints and links. Inter-node RCCL traffic used NET/Socket over the guest NICs or, in emulated KFD mode, the node network endpoints on host loopback. GPU VRAM was separate per GPU and per node; the collectives did not synchronize through one shared HBM allocation.

    The QEMU guest loaded an AMDGPU/AMDKFD module built from the pinned DKMS package with zero local driver patches. The pinned driver's observed local peer path was UC PCIe peer BAR mapping. RCCL used P2P/IPC locally and NET/Socket across guests. The node-local fabric carried the local peer memory effects behind that PCIe mapping. This does not establish native xGMI discovery, mapping, or traffic. The emulated KFD run selected ROCr's public HSA_ENABLE_IPC_MODE_LEGACY=1 option; default IPC mode is not qualified.

    The checkout was at 07988db4b20d25ddf8cab50a008791255ec96532 with uncommitted changes. No commit was created. The complete records and logs are preserved under tmp/same-host-stock-transport-20261015/evidence/.

    Transport and software inputs¶

    The four QEMU guests each had four vCPUs, 12 GiB RAM, two VFIO-user PCI GPUs, and one virtio-net-pci NIC. Their NICs used 10.77.0.1 through 10.77.0.4 on multicast segment 239.192.14.1:46617. QEMU was built from 10.1.0 commit f8b2f64e2336a28bf0d50b6ef8a7d8c013e9bcf3 with only three general PCIe fixes: preserve the VFIO-user PCI class code, give the XIO3130 downstream port a valid LinkCap, and advertise opt-in root AtomicOp completion and switch routing for implemented guest-RAM atomics. There is no rocJITsu-specific VFIO-user command, trailer, capability, or QEMU device property. Standard descriptorless VFIO_USER_DMA_MAP messages identify peer BAR IOVAs; the server resolves them against its live PCI BAR decoder.

    The server used libvfio-user source revision 37491ed9af828fc161238dacd82e83ea35a09f87 with only the generic sub-4-GiB 64-bit BAR upper-address mask fix. That fix is required for the guest's peer BAR address to survive configuration writes; it is a library bug-fix candidate, not a private transport. A pre-fix regression observed a zeroed upper BAR register and a failed peer read; the fixed regression and standard-transport two-GPU guest probe passed.

    Directed effects, teardown, and regressions¶

    Each node's forward and reverse local GPU route committed peer writes. Individual effect records matched the route totals and reported zero drops. There were no peer reads in this RCCL run; the separate two-GPU guest probe read and wrote GPU0 from GPU1, checked the numerical result, and recorded one four-byte read and one four-byte write on route 1251 -> 1250.

    The VFIO nodes captured 34,899 effects each; emulated nodes captured 36,297 each. All eight node processes exited zero within their bound. Guest logs reported both AMDGPU-bound devices and orderly completion, with no BUG:, WARNING:, Call Trace:, FATAL:, UBSAN:, or numerical failure. RCCL did print a nonfatal warning that AMD SMI fabric support was disabled; no native xGMI path is claimed. No VFIO-user or daemon socket remained. The focused VFIO host and grant regression selection passed 42/42 tests. The revised VFIO launcher suite passed 54/54 tests. git diff --check, bash -n on the QEMU fix applicator, and Python compilation of both controllers passed.

    This qualifies the smaller same-host pod-style configuration with UC PCIe peer mappings over the modeled local fabric. Native xGMI driver discovery, cacheable peer coherence, default ROCr IPC mode, and the two-host run are separate gates.
