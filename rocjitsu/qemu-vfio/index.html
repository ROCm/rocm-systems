    QEMU VFIO-user compute¶

    This guide describes the QEMU/VFIO-user path that rocJITsu supports today. The single-GPU guest qualification recipe uses configs/gfx1250_mi455x.json. The launcher can also expose multiple local gfx1250 GPUs from a matching configuration, including configs/gfx1250_mi455x_kmd_4gpu.json. QEMU owns the guest, while rocJITsu supplies the emulated PCI devices and GPU models.

    The repository provides the VFIO-user server and scripts/run-vfio-guest.py. It does not build or distribute a guest kernel, initramfs, AMDGPU package, ROCm runtime, or rocBLAS payload. Those inputs must come from one mutually compatible public release or nightly. Record their versions and SHA-256 digests when publishing a result. The pod guest payload recipe pins the external QEMU, libvfio-user, driver, kernel, and ROCm inputs used by the same-host peer/RCCL gates. It also distinguishes the zero-patch final driver module from earlier diagnostic patch runs. The four-node VFIO pod controller uses configs/gfx1250_mi455x_kmd_4node_2gpu_if.json to launch the mixed local peer and inter-node NET workload described by that recipe.

    Standard peer BAR transport¶

    The pinned QEMU sends a standard, descriptorless VFIO_USER_DMA_MAP when a requester maps another GPU's PCI BAR. The VFIO host decodes that IOVA against the live 64-bit BAR registers of the other functions in the same server-local node. It accepts only one unambiguous, fully covered BAR0 mapping backed by a sealed, stable-size memfd. The map is bound to both live transport sessions; exact UNMAP, BAR reprogramming, reset, and disconnect revoke it. A stale peer IOVA is denied rather than reinterpreted as ordinary guest RAM. GPU peer effects cross the modeled local fabric. Ordinary guest RAM uses its usual descriptor-backed VFIO-user DMA map and never routes through the GPU fabric.

    The active libvfio-user source carries only a generic fix for the upper address register of a sub-4-GiB 64-bit BAR. A former nonstandard peer transport is removed from the active source and launch path. Runs that depended on it are historical controls, not evidence for the current stock-transport gate. The peer endpoint does not advertise AtomicOp completion; peer BAR atomics are rejected. The selected stock driver emits UC peer PTEs, so cacheable peer coherence is a later gate.

    GPU VM hardware path¶

    The guest uses the selected AMDGPU and AMDKFD driver with the ordinary GFXHUB, MMHUB, NBIF/HDP, and KFD VM register and packet paths. BAR4 contains only the MSI-X table and pending bits (8 KiB). The GFXHUB VMID-0 invalidation request publishes the configured GART translator before its ACK bit is exposed. Both hub models answer their versioned invalidation registers, and the NBIF 7.11 remap accepts the driver's HDP flush write. A PCI page-table walk retains a lease on the transport session it captured, so reset or detach cannot redirect that walk to a later session.

    Nonzero-VMID GFX12 translations rewalk their page tables on each query. The current functional model therefore has no retained UTC/TLB entries for a hub invalidation to discard before its ACK. Any future translation cache must be a separate Simdojo hardware component reached by the versioned hub request; its selected VMID state must retire before the hub exposes completion.

    The PCI function is a Simdojo component. Versioned IP block adapters own the register claims and control handshakes for the blocks the discovery table publishes; the SoC's GPU VM, queues, memory, and fabric models own data effects. Additional IOMMU, memory-controller, MMHUB, or translation-cache behavior must attach at those hardware boundaries and use the driver's existing registers or packets. A register write alone cannot establish cacheable visibility or retirement.

    Those behaviors support functional GPU memory translation. They do not prove that CPU-written PTEs have a cacheable publication order or that a peer PTE has a cacheable memory type. The observed stock-driver peer PTE was UC, so peer cache fills remain disabled. A nonzero-VMID peer PTE with any other memory type is rejected before its PCI backing effect. Translated vector reads whose full line maps to local VRAM can use the existing Simdojo V$ and L2 cache components. Their tags retain the exact address-space handle, selected physical line, raw PTE memory type, permissions, and local visibility epoch. Local VRAM writes, HDP flushes, and fabric maintenance retire those clean local tags. Translated scalar reads and vector stores still use direct VM access, and cacheable peer fills remain unqualified. GFX12 translations retain the exact PTE memory-type encoding alongside the broad cache policy, so a deferred rewalk also rejects an NC-to-RW PTE change. VMID-0 GART transfers are unaffected because MES and SDMA do not issue CU cache fills. A coherent peer cache result still requires versioned hub/TLB invalidation and exact VM/PTE and grant identity through fills, maintenance, effects, and retirement. Those states must be driven by the stock driver's registers and packets. Results from retired experiments do not qualify the current stock-driver cache path.

    Same-host stock-driver control¶

    On 2026-10-14, a fresh guest image built from the pinned DKMS package with driver bug-fix patches 0001 through 0008 bound two gfx1250 GPUs. With the corrected XIO3130 LinkCap and explicit root AtomicOp completion for mapped guest RAM, a GPU1 kernel read and wrote GPU0 VRAM. The guest checked observed=0x13579bdf and final_owner=0x1357c047; the server counted one committed read and write from GPU1 to GPU0. The guest exited zero without a kernel UBSAN or WARNING. A three-second wait after workload exit let the asynchronous KFD process release finish before the test guest's forced poweroff; it also removed the shutdown BO-free warning seen with immediate poweroff. The driver module was unchanged between those runs.

    With root and switch AtomicOp properties left off, the same driver bound both PCI functions, but KFD rejected PCIe atomics and HIP reported no ROCm-capable device. The working run enabled root completion and switch routing for the VFIO backend's guest-RAM atomic operations. The peer endpoint's AtomicOp completer bits stayed clear, and peer BAR atomics are rejected. This checks ordinary peer reads and writes on one host; it does not qualify peer atomics, cacheable coherence, or the four-guest same-host RCCL exit gate below. The exact local images, commands, hashes, and log paths are in docs/stock-driver-hardware-path-20261014.md.

    Host prerequisites¶

    • Linux on x86-64.
    • CMake 3.28 or newer for a VFIO-enabled build.
    • Linux UAPI headers containing the VFIO migration and DMA logging interfaces used by libvfio-user (Linux 6.1 or newer is a practical baseline).
    • Ninja and a supported C++20 compiler.
    • Python 3.10 or newer for the launcher.
    • QEMU with the vfio-user-pci device.
    • Internet access during the first CMake configure, unless the fetched libvfio-user and json-c dependencies are already available locally.
    • Optional access to /dev/kvm. The launcher falls back to TCG.

    Check the QEMU capabilities before building a guest:

    qemu-system-x86_64 -accel help
qemu-system-x86_64 -device help | rg vfio-user-pci

    Build the VFIO-user server¶

    Run these commands from the rocjitsu source directory:

    cmake -S . -B build-vfio -G Ninja \
  -DCMAKE_BUILD_TYPE=Release \
  -DROCJITSU_ENABLE_VFIO=ON
cmake --build build-vfio --target rocjitsu_bin rj_ip_discovery

    The VFIO dependency gate runs during configuration and rejects CMake older than 3.28 while leaving the ordinary build's 3.22 minimum unchanged.

    The resulting server is:

    build-vfio/tools/rocjitsu/rocjitsu

    The build also produces the profile-specific IP-discovery generator at:

    build-vfio/tools/rj-ip-discovery/rj-ip-discovery

    Prepare compatible guest artifacts¶

    The kernel, AMDGPU module, firmware, ROCm user-mode stack, and rocBLAS payload must be mutually compatible. A current ROCm nightly is suitable when it has gfx1250 support and its AMDGPU driver contains commit 4e07da515d1c (drm/amdgpu: enumerate UMSCH HW IP) or an equivalent backport. That fix allows discovery of this compute-only device without a VCN instance.

    The gfx1250 profile intentionally omits display and media IP such as JPEG, VCN, and UVD. It retains the management-processor discovery records required by the driver; those records do not imply a complete firmware-managed hardware model. This does not mean that the Linux driver never opens firmware files. With direct firmware loading, current AMDGPU code still parses firmware for the enabled compute, MES, SDMA, and IMU paths. Package the firmware files that match the exact AMDGPU module in the initramfs. The authoritative inventory for a built module is:

    modinfo -F firmware /path/to/amdgpu.ko | sort -u

    For the current gfx1250 path, requests can include amdgpu/gc_12_1_0_imu.bin, amdgpu/gc_12_1_0_mec.bin, amdgpu/gc_12_1_0_rlc_1.bin, a matching gfx1250 MES image, and amdgpu/sdma_7_1_0.bin. Use files from the same public driver/firmware release. Do not add JPEG or VCN firmware, because those IP blocks are absent.

    The launch command below selects file-based IP discovery with amdgpu.discovery=2. Its amdgpu/ip_discovery.bin is not a vendor firmware blob and must not be copied from an unrelated package. Generate it from the same rocJITsu gfx1250 profile used by the emulated device:

    mkdir -p /path/to/staging-root/lib/firmware/amdgpu
build-vfio/tools/rj-ip-discovery/rj-ip-discovery \
  gfx1250 \
  /path/to/staging-root/lib/firmware/amdgpu/ip_discovery.bin

    Regenerate the table whenever the rocJITsu device profile changes, then pack that staging tree into the initramfs.

    The initramfs must contain:

    • an executable /init;
    • /dev, /proc, and /sys mount points;
    • the guest kernel's AMDGPU module and all of its module dependencies;
    • every firmware file requested by the selected gfx1250 driver path;
    • the dynamic loader and transitive libraries needed by the workload;
    • a gfx1250-capable ROCr/HIP runtime, rocBLAS, its gfx1250 Tensile metadata and code object, and a GEMM validation executable;
    • a shutdown command such as BusyBox poweroff.

    The init process must:

    1. Mount devtmpfs, procfs, and sysfs.
    2. Load the AMDGPU module and its dependencies.
    3. Fail if AMDGPU did not bind the 0x1002:0x75c1 PCI function.
    4. Fail if /dev/kfd is absent.
    5. Run the GEMM validator and propagate its result.
    6. Print stable success or failure markers.
    7. Power the guest off. QEMU runs with -no-reboot, so poweroff is the normal successful exit path.

    Use a fresh staging directory and an ordinary initramfs builder, or pack a reviewed staging tree directly:

    (
  cd /path/to/staging-root
  find . -print0 | cpio --null --create --format=newc
) | gzip -9 > /path/to/gfx1250-compute-initramfs.gz

    Do not copy an arbitrary host /opt/rocm tree. Copy the selected package payloads and all transitive ELF dependencies, preserve symlinks, and verify that the rocBLAS library data contains a gfx1250 code object. A missing loader, library, Tensile data file, or firmware file normally appears as a probe or workload failure rather than as a host-launch failure.

    Historical AMDGPU driver bug-fix runs¶

    The final same-host pod image uses the pinned AMDGPU/AMDKFD package with zero local driver patches. Earlier fault-injection and four-GPU controls used locally patched guest modules. Those patches are not included in this repository and their results are historical; they do not qualify the current stock-driver pod image. See the historical October 14 record and zero-patch pod ablation for the scope of those runs.

    GEMM qualification contract¶

    A useful qualification workload calls rocblas_sgemm and compares every output element against a CPU reference. The reference qualification used an FP32, column-major, non-transposed 128 x 128 x 128 multiply with alpha 1 and beta 0. Its inputs were deterministic. A validator can expose this stable log contract:

    guest: /dev/kfd present
sgemm-validator: api=rocblas_sgemm ... m=128 n=128 k=128 alpha=1 beta=0
sgemm-validator: max_absolute_error=... failures=0
sgemm-validator: PASS
guest: done

    Do not qualify the device merely because the kernel probed or a kernel was submitted. Require numerical validation, a zero-status QEMU exit, and orderly rocJITsu shutdown. The packaged rocBLAS installation must select a supported gfx1250 backend and find its matching library data without runtime environment overrides.

    Launch the guest¶

    Choose a short output path because Unix-domain socket paths are limited. The output directory must not already exist.

    QEMU=/path/to/qemu-system-x86_64
KERNEL=/path/to/vmlinuz
INITRAMFS=/path/to/gfx1250-compute-initramfs.gz
ROCJITSU=build-vfio/tools/rocjitsu/rocjitsu
OUTPUT=/tmp/rocjitsu-gemm-run

python3 scripts/run-vfio-guest.py \
  --qemu "${QEMU}" \
  --kernel "${KERNEL}" \
  --initramfs "${INITRAMFS}" \
  --rocjitsu "${ROCJITSU}" \
  --config configs/gfx1250_mi455x.json \
  --output "${OUTPUT}" \
  --accel auto \
  --memory 4G \
  --probe-timeout 10 \
  --startup-timeout 60 \
  --append 'console=ttyS0 rdinit=/init panic=-1 amdgpu.discovery=2 amdgpu.emu_mode=1 amdgpu.fw_load_type=0 amdgpu.vm_update_mode=3 amdgpu.gpu_recovery=0 amdgpu.vramlimit=1024 amdgpu.ip_block_mask=0x3f rocjitsu.workload=sgemm' \
  --expect-log 'guest: /dev/kfd present' \
  --expect-log 'sgemm-validator: PASS' \
  --reject-log 'sgemm-validator: FAIL' \
  --reject-log 'guest: FATAL:'

    The 1 GiB VRAM limit leaves enough guest VRAM for ROCr to provision queue scratch at the device's advertised occupancy. A smaller limit can be adequate for scratch-free kernels but may make a private-segment dispatch wait indefinitely for scratch allocation.

    The repository does not provide the validator binary, so make the guest validator emit the example markers above or replace the --expect-log and --reject-log values with its stable public output.

    --accel auto selects KVM when QEMU advertises it and /dev/kvm is usable; otherwise it selects TCG. KVM and TCG both expose the same VFIO-user device. TCG is slower but avoids a host KVM dependency. --smp sets the guest virtual CPU count; its default is one. The four-rank RCCL P2P guest below uses --smp 4.

    Run the same command with --dry-run first. Dry-run validates all input paths and executable permissions, confirms that QEMU provides vfio-user-pci, asks the selected rocJITsu binary to confirm that it was built with VFIO-user support, selects the accelerator, prints the exact server and QEMU argument vectors, and does not create the output directory.

    Each QEMU or rocJITsu capability probe is limited to --probe-timeout seconds (10 by default). SIGTERM or SIGINT sent to the launcher while a probe is running terminates and reaps that probe before the launcher exits.

    The launcher waits at most --startup-timeout seconds (60 by default) for the server to create and explicitly announce its listening socket. It then checks the socket, creates shared memfd-backed guest RAM, and starts:

    rocjitsu --config configs/gfx1250_mi455x.json \
  --vfio-socket <output>/vfio-user.sock

    and connects QEMU's vfio-user-pci device to that socket. Shared guest RAM is required so the VFIO-user server can map DMA windows.

    Expose multiple local GPUs¶

    Repeat --socket once for each local GPU, in GPU ordinal order. Every socket must have a distinct, short path directly inside the new output directory. The paths are the complete ordered local GPU list; specifying one --socket does not append the default socket. The default remains <output>/vfio-user.sock when no --socket is specified. rocJITsu validates the socket count against the selected configuration or local node.

    For the repository's four-GPU configuration, use the same prepared guest inputs and kernel command line as above, with four explicit sockets:

    The preset uses PCI ID 0x1002:0x75c1 for every GPU, matching the single-GPU guest contract. The guest must discover four distinct BDFs and confirm that AMDGPU binds each one before running per-GPU numerical checks.

    OUTPUT=/tmp/rocjitsu-four-gpu-run

python3 scripts/run-vfio-guest.py \
  --qemu "${QEMU}" \
  --kernel "${KERNEL}" \
  --initramfs "${INITRAMFS}" \
  --rocjitsu "${ROCJITSU}" \
  --config configs/gfx1250_mi455x_kmd_4gpu.json \
  --output "${OUTPUT}" \
  --socket "${OUTPUT}/gpu0.sock" \
  --socket "${OUTPUT}/gpu1.sock" \
  --socket "${OUTPUT}/gpu2.sock" \
  --socket "${OUTPUT}/gpu3.sock" \
  --accel auto \
  --memory 4G \
  --append 'console=ttyS0 rdinit=/init panic=-1 amdgpu.discovery=2 amdgpu.emu_mode=1 amdgpu.fw_load_type=0 amdgpu.vm_update_mode=3 amdgpu.gpu_recovery=0 amdgpu.vramlimit=1024 amdgpu.ip_block_mask=0x3f rocjitsu.workload=sgemm'

    The probe-free eight-patch guest enumerated and bound all four PCI functions at 0000:00:04.0 through 0000:00:07.0. A second image selected each GPU by HIP_VISIBLE_DEVICES, checked that HIP reported the expected BDF, and ran the reference-checked FP32 128-by-128 SGEMM on each one. All four runs reported zero failures and zero maximum absolute error. The two preexisting startup WARNs remained. Inputs, commands, hashes, and logs are in tmp/p3v-four-gpu-eightpatch/BUILD-RECORD.md. These runs qualify four local compute paths under the replicated preset; they do not check peer access.

    To use the explicit four-GPU scale-up schematic instead of the legacy replicated preset, replace the config argument above with --config configs/gfx1250_mi455x_4gpu_scaleup.json and add --node node0. Keep all four sockets and the same guest inputs. This graph projects local fabric routes but does not advertise KFD peer links. Its 1 GiB BAR0 aperture per GPU covers the guide's 1 GiB guest VRAM limit; this is a simulator guest setting, not a physical BAR claim. The per-GPU GEMM check validates local compute only; the larger BAR does not qualify guest P2P or RCCL.

    Use --node <id> with a system manifest to select the local node served by this process; rocJITsu checks the selection. The launcher starts one rocJITsu server and waits for one readiness signal, then checks that every requested socket exists before starting QEMU. For multiple GPUs, QEMU receives one vfio-user-pci device per socket on pcie.0 at slots 0x4, 0x5, and so on, with IDs rocjitsu-gpu-0, rocjitsu-gpu-1, and so on. The single-GPU QEMU device arguments remain unchanged.

    The existing GEMM qualification contract covers one GPU. A multi-GPU launch does not by itself establish guest PCI enumeration, peer DMA, RCCL operation, or numerical correctness. Check the actual guest BDFs and validate the intended multi-GPU workload before reporting such a result.

    Build QEMU with general PCIe fixes¶

    The tested QEMU source is 10.1.0 commit f8b2f64e2336a28bf0d50b6ef8a7d8c013e9bcf3. Apply the repository's general PCIe fixes to a clean checkout, then build in a separate directory:

    QEMU_SOURCE=/path/to/qemu-10.1-source
QEMU_BUILD=/path/to/qemu-10.1-build
scripts/apply-qemu-pcie-fixes.sh "$QEMU_SOURCE"
mkdir -p "$QEMU_BUILD"
(
  cd "$QEMU_BUILD"
  "$QEMU_SOURCE/configure" --target-list=x86_64-softmmu --enable-kvm \
    --disable-docs --disable-tools --disable-guest-agent --disable-werror
  ninja qemu-system-x86_64
)

    The script fixes QEMU VFIO-user's class-code default so the guest retains the device's compute class. qemu-10.1-xio3130-link-capability.patch fixes a separate PCIe bridge defect: QEMU 10.1 otherwise publishes zero speed and width in each XIO3130 downstream port's LinkCap, even though its LinkSta reports Gen1 x1. The selected AMDGPU driver reads that parent LinkCap when it initializes PCIe bandwidth, and zero width leaves KFD with an empty lane mask. The patch gives the port valid Gen1 x1 defaults through QEMU's ordinary link properties. It changes no guest driver code or PCIe AtomicOp capability. qemu-10.1-pcie-atomic-capabilities.patch adds root port 32-bit and 64-bit completer properties and PCIe switch routing property default to off. The VFIO DMA backend completes aligned 32-bit and 64-bit atomics on mapped guest RAM; the launcher enables those PCIe bits only with --p2v-atomic-root. The peer GPU endpoint continues to advertise no AtomicOp completion, and the server rejects atomics aimed at a peer BAR grant.

    These QEMU fixes do not change the VFIO-user protocol. Standard descriptorless peer BAR DMA maps carry no owner trailer or socket ordinal; the server resolves them through its live PCI BAR address decoder. For a two- or four-GPU peer-admission diagnostic, pass --p2v-switch-topology. It places every ordered GPU socket behind its own downstream port of one X3130 switch. The option requires exactly two or four sockets and does not change the default PCI layout. A four-GPU run also needs BAR0 to cover each GPU's used VRAM; the default 256 MiB aperture with a 1 GiB guest VRAM limit is insufficient for peer admission. The switch option alone does not qualify peer mappings or coherent traffic. Preserve the exact QEMU source commit, patch choice, binary hash, launcher arguments, and server binary hash in the run record.

    The selected gfx1250 AMDKFD driver requires PCIe atomics to guest RAM before it exposes a ROCm device. For the two-GPU switch path, pass --p2v-atomic-root only with a server that implements aligned guest-RAM atomics. The launcher checks that patched QEMU exposes the root and switch properties, then enables both root completion widths and routing on that switch path. Without this option, the capabilities stay off and the current guest reaches hipGetDeviceCount with no ROCm-capable device. This option does not qualify peer BAR atomics, cacheable peer access, or coherent fabric.

    Guest P2V qualification requires a requester kernel to read and write owner VRAM and the owner to read back the expected value. For the prepared g7 HIP probe, require one p2v-hip: numerical line with observed=0x13579bdf, final_owner=0x1357c047, matching expected fields, and result=PASS, plus zero-status guest exit and orderly server shutdown. A successful KFD peer map, requester PTE update, HIP launch, or synchronize alone is insufficient. No guest P2V or AtomicOp result is qualified by the patch or launcher option alone.

    Four-GPU fixture peer and RCCL results¶

    With the probe-free eight-patch module, the four-GPU guest numerically checked requester GPU1 reading and writing owner GPU0 VRAM. An expanded HIP probe passed the same sentinel and final-owner checks on all 12 directed GPU pairs; the server recorded one committed read and write on every matching route. The guest used a nonstandard peer transport and a diagnostic switch that advertises AtomicOp routing bits for peer-map admission. These probes did not execute an AtomicOp.

    The four-rank RCCL P2P guest then passed AllReduce, Broadcast, AllGather, ReduceScatter, and SendRecv on all four ranks, with 20 passing reference results and four distinct bus IDs. Its logs showed P2P/IPC data channels, and the server recorded writes on eight directed fabric routes. Exact images, binaries, commands, hashes, and logs are in tmp/p3v-four-gpu-eightpatch/BUILD-RECORD.md. These results establish functional peer reads and writes and numerical RCCL P2P under this diagnostic setup. Cacheable coherence, AtomicOp completion, and the remaining VM error paths remain unqualified. Peer cache fills stay disabled.

    Older guest experiments used unsupported interfaces and are excluded from this qualification. Their numerical results do not qualify cacheable coherence or peer AtomicOp completion.

    A separate size-controlled four-vCPU diagnostic passed all five RCCL cases at 1,024 and 262,144 total FP32 elements, with three host-reference-checked iterations per rank. The endpoint now reports successful backing bytes as well as effect counts per directed route. Source-matched RCCL tuning logs selected RING/LL for the four small collectives and RING/SIMPLE for the large ones; SendRecv reported P2P setup completion on every rank. Each run logged completed legacy IPC buffer imports on every rank, and no selected P2P/IPC send connector used /read or /CE. The large isolated cases recorded 59,782,752 aggregate committed backing-write bytes and 118,476 writes across the twelve directed routes; all peer read counters were zero. The exact image, binaries, commands, per-case totals, route counters, and log hashes are in tmp/p4b/BUILD-RECORD.md and tmp/p4b/matrix-summary.json. These byte totals may include transport metadata and do not identify payload backing ranges or match each IPC import to a particular fabric effect. Guest KFD MAP identity, cacheable visibility, checked GART publication, and a release-compatible firmware tuple remain unqualified.

    For a VFIO diagnostic with at least two functions, pass --fabric-effect-trace to the launcher. The server reserves room for 200,000 committed directed effects before serving, then reports each effect's request ID, requester/owner GPU IDs, operation, canonical backing ID and offset, byte count, target-map ID, requester GPU VA, and IOVA at shutdown. The opt-in trace records no failed or queued effect. It reports overflow and exits with an error if any effect was dropped. Run python3 scripts/check-vfio-fabric-trace.py SERVER_LOG CASE_SUMMARY_JSON GUEST_LOG CONFIG_JSON for the four-rank RCCL fixture. The checker matches every record with directed counts and byte totals, the host-reference case summary, and exactly one completed RCCL IPC import range in the requester's rank log. It resolves each rank's bus ID to a GPU ID using the four-GPU configuration. The map ID belongs to the QEMU/VFIO target grant. A VA match to an RCCL import range does not identify the guest KFD MAP handle, the selected channel, or application payload bytes.

    An earlier diagnostic guest used an additional KFD import/MAP trace and the checker's --require-kfd-map option. That guest patch is not included here or required by the current gate. Its logs joined the requester's rank PID, KFD handle and VA extent, guest KFD GPU IDs, and RCCL import range to each fabric effect. A completed MAP record does not prove its lifetime at the later effect, the connector channel, or the application payload handoff.

    Connect guest NICs for a NET/Socket control¶

    The launcher adds no NIC by default. To connect two independently launched guests over QEMU's socket Ethernet backend, add one of these option pairs to each otherwise complete launch command:

    node0: --net-socket-listen 127.0.0.1:17000 --net-mac 02:00:00:00:00:01
node1: --net-socket-connect 127.0.0.1:17000 --net-mac 02:00:00:00:00:02

    Start the listening launcher first. Wait until its QEMU process binds the host TCP port (for a local run, inspect the listening port with ss -ltn), then start the connector while the listener remains running. A TCP connect probe can consume QEMU's single peer connection. Use separate output directories and VFIO sockets. Select --node node0 and --node node1 with the two-node system manifest. On different hosts, bind the listener to an address reachable by the connector and open that TCP port. Each endpoint must be numeric IPv4 with a port from 1 to 65535, and each NIC needs a distinct unicast MAC. The NIC uses Q35 PCI slot 0x8, leaving slots 0x4 through 0x7 for up to four GPU functions.

    The socket endpoint is a host transport address; it does not assign guest IP addresses. The guest image must bring up its virtio NIC, configure distinct addresses and a route, and check peer connectivity. RCCL also connects to its own advertised guest IP during bootstrap, so bring up loopback and check a local TCP connection. Give the two guests distinct hostnames or NCCL_HOSTID values so RCCL identifies them as separate nodes.

    After mounting devtmpfs on /dev, create and mount /dev/shm before starting RCCL:

    mkdir -p /dev/shm
mount -t tmpfs -o mode=1777,nodev,nosuid tmpfs /dev/shm
ip link set lo up

    The selected RCCL library checks /dev/shm during communicator setup even when NCCL_SHM_DISABLE=1; creating it in the staging root before the devtmpfs mount is insufficient.

    The hip_rccl_gfx1250_test rank binary supports a two-guest TCP bootstrap. Build it with cmake --build build-vfio --target hip_rccl_gfx1250_test_target, then package it with matched librccl, its transitive ELF dependencies, and the gfx1250 RCCL code object. Rank 0 uses --rank=0 --world-size=2 and --bootstrap-listen=GUEST_IP:PORT; rank 1 uses --rank=1 --world-size=2 and --bootstrap-connect=RANK0_GUEST_IP:PORT. Generate a fresh 128-bit hexadecimal run ID for each pair, for example with python3 -c 'import secrets; print(secrets.token_hex(16))'. Pass it to both ranks as --bootstrap-run-id=ID. Use the same seed, test filter, and --bootstrap-timeout-ms, and assert --expected-devices=1 on each guest. These bootstrap addresses are guest IPs, separate from QEMU's host socket endpoints. Existing daemon tests still use --shared-dir.

    Set NCCL_NET=Socket, NCCL_SOCKET_IFNAME to the guest NIC, and disable IB, P2P, and SHM for the NET control. Require numerical GoogleTest success on both ranks and NET/Socket channel evidence. The bootstrap timeout covers only its handshake and case exchange; the paired guest controller must also bound the complete run and clean up both guest processes on failure.

    Results and reruns¶

    The launcher writes:

    <output>/guest.log
<output>/server.log

    Success requires all requested log markers, no rejected marker, QEMU status zero, and cooperative rocJITsu termination. The launcher sends SIGTERM to the server after QEMU exits and waits up to five seconds for it to stop cleanly. After that grace period it sends SIGKILL, reaps the server, and fails the run. Any server exit while QEMU is still running fails the run, regardless of exit status. An orderly guest disconnect does not terminate the server; it remains alive until the launcher observes QEMU exit and requests shutdown.

    Each run needs a new output directory. Preserve the logs together with:

    • the rocJITsu Git commit;
    • the QEMU version;
    • the accelerator selected by dry-run;
    • kernel, initramfs, AMDGPU package, firmware package, and ROCm package versions and SHA-256 digests;
    • the exact kernel command line;
    • the GEMM dimensions, input definition, reference calculation, and acceptance tolerance.

    Troubleshooting¶

    QEMU does not recognize vfio-user-pci¶

    Use a QEMU build with VFIO-user PCI support. This is distinct from the host-kernel VFIO passthrough devices.

    The server does not report readiness¶

    Inspect server.log. Also keep the output path short and ensure that no stale path already exists. The socket must be directly inside the output directory. The launcher waits on a pipe inherited by rocJITsu, which reports readiness after configuration parsing, topology construction, engine startup, and the final socket bind. Process exit or a closed pipe reports startup failure immediately; a live server that does not report readiness receives SIGTERM after --startup-timeout seconds and is force-killed if it cannot complete the bounded shutdown handshake.

    AMDGPU reports a missing firmware file¶

    Copy the named file from the firmware package matching the guest AMDGPU module, then rebuild the initramfs. Absence of JPEG/VCN hardware only removes media firmware requirements; it does not remove compute, MES, SDMA, IMU, or IP-discovery parser inputs.

    AMDGPU fails while discovering multimedia IP¶

    Use a driver containing 4e07da515d1c or its backport. Do not work around this by adding a fake JPEG or VCN device to rocJITsu.

    /dev/kfd is absent¶

    Check guest.log for the first AMDGPU probe failure. Verify the PCI ID, module/kernel match, firmware inventory, kernel configuration, and the compute-only IP-block mask before debugging ROCm user space.

    rocBLAS cannot find a kernel¶

    Verify that the guest contains the gfx1250 Tensile metadata and code object from the same rocBLAS package as librocblas.so. Do not substitute files from another GPU target.

    The run stops making progress¶

    The launcher does not impose a runtime deadline. It waits for QEMU to exit and fails immediately if rocJITsu exits first. A normal guest disconnect leaves the server alive until the launcher observes QEMU's exit and requests shutdown, so this ordering needs no grace period. Use the partial guest.log and server.log to distinguish slow progress from a deadlock. CI systems can enforce a job-level budget without changing launcher behavior. If that budget sends SIGTERM or SIGINT to the launcher, it terminates and reaps both children and removes the owned VFIO sockets before exiting. SIGKILL cannot provide cooperative cleanup.
