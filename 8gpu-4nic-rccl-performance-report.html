1. Executive Summary

ByteDance (BD) reported that their 2-node, 8-GPU (MI308), 4-NIC (Pollara 400) cluster was delivering significantly lower RCCL performance for Data Parallelism (DP) workloads compared to their NVIDIA BF3-mini NIC baseline and our internal test results. The DP use case uses NCCL_TESTS_SPLIT_MASK=0x7 to bypass XGMI and route all traffic through the AINICs only.

The root cause was identified as a PCIe topology visibility issue: without the Broadcom PCIe switch inter-switch virtual links being exposed to the OS, RCCL perceived certain GPU↔NIC paths as too distant (PHB instead of PXB), causing it to disable GPU Direct RDMA (GDR) for those GPU/NIC pairs. This forced traffic through slower CPU-mediated paths.

The fix required two changes:

  1. A Linux kernel patch to enable Broadcom PCIe switch virtual link discovery (with a minor modification to bypass the SECURE_PART check).
    Patches: LKML Part 1  |  LKML Part 2
  2. A private RCCL patch (by Wenkai Du, ROCm team) to correctly handle new topology models when virtual switch links are present.
    PR: ROCm/rocm-systems PR #3121 — "Add new models when virtual switch links are present"

Both fixes must be applied together. The kernel patch alone causes a regression in global AllReduce (~194 GB/s → ~90 GB/s).

With both fixes applied, DP AllReduce performance recovered to ~24 GB/s (target) and global AllReduce maintained ~194 GB/s, matching expectations.

2. Background & Context

What is Data Parallelism (DP) testing?

In a multi-GPU training system, the 8 GPUs within a node are typically connected via XGMI (inter-GPU fabric). For Data Parallelism workloads, each GPU independently processes different data shards and only communicates gradients via the network NICs (not XGMI). The flag NCCL_TESTS_SPLIT_MASK=0x7 simulates this by forcing RCCL to bypass XGMI and route all collective traffic exclusively through the AINICs (Pollara 400 NICs).

The target DP performance is ~24 GB/s for both AllReduce (AR) and AllToAll (A2A), matching numbers achieved by the competing BF3-mini NIC on the same MI308 GPU platform.

When running RCCL collective tests with NCCL_TESTS_SPLIT_MASK=0x7 (DP mode), BD's MI308 + Pollara setup showed significantly lower performance compared to both the BF3-mini reference and AMD internal test results:

5. Root Cause Analysis

The Core Issue: Two Combined Factors

Two architectural factors combine to push the GPU↔NIC PCIe distance past RCCL's GDR threshold in split-mask (DP) mode:

Factor 1: Broadcom PEX89104 Multi-Host Partitioning

Each physical PEX89104 PCIe Gen5 switch is configured with two upstream (host-facing) ports, each connecting to a different CPU PCIe root port. This is a switch firmware-level configuration (MFG/EEPROM) that partitions one physical switch into two independent OS-visible PCIe hierarchies.

From the Broadcom switch's own pciehostview: 

ONE Physical PEX89104 Switch:
  Host Port 80 (→ CPU root 00:01.1):  DS Port 0 = GPU0,  DS Port 16 = NIC0
  Host Port 32 (→ CPU root 20:01.1):  DS Port 96 = NIC1, DS Port 112 = GPU1

The OS sees two completely separate PCIe trees — it has no way to know they share a physical switch without the kernel switch_discovery module reading Broadcom's proprietary VSEC (Vendor-Specific Extended Capability) registers. 

OS view:                                    Physical reality:
                                            ┌──────────────────────────────┐
00:01.1 → 01:00.0 (BRCM upstream A)        │   ONE PEX89104 Switch        │
  ├─ GPU0  (DS Port 0)            ◄─────────│   Host Port 80 (x16)        │
  └─ NIC0  (DS Port 16)                     │         │                   │
                                            │   internal fabric            │
20:01.1 → 21:00.0 (BRCM upstream B)        │         │                   │
  ├─ NIC1  (DS Port 96)           ◄─────────│   Host Port 32 (x16)        │
  └─ GPU1  (DS Port 112)                    │                             │
                                            └──────────────────────────────┘

Why two host ports? A single Gen5 x16 upstream provides 64 GB/s. A GPU (x16) + NIC (x16) + NVMe (x4) would oversubscribe one upstream. Two x16 upstreams give 128 GB/s total host bandwidth, and each can be wired to a different NUMA node for locality.

Can this be changed to single-host mode? Technically yes — the PEX89104 supports both single-host (base mode) and multi-host (synthetic mode). However, the port-to-host mapping is defined in the switch's EEPROM/MFG firmware (programmed by the OEM via Broadcom's SDK tools), not a BIOS setting. Switching to single-host would also create a bandwidth bottleneck: 36 lanes of downstream devices (GPU x16 + NIC x16 + NVMe x4) on a single x16 upstream link. The kernel patch + RCCL fix is the correct solution — it preserves the multi-host bandwidth benefits while making RCCL aware of the true physical topology.

Factor 2: MI300X Internal PCIe Bridge

The AMD MI300X is a multi-chiplet SoC (8 XCDs + 4 AIDs). It presents as a PCIe switch rather than a direct endpoint, because only AID0's NBIO block manages the host PCIe link and must route traffic to internal blocks (SDMA, HDP, NBIO) across multiple chiplet dies: 

PCI bridge:    AMD     [1022:1500]   ← Top-level upstream bridge (AID0 NBIO)
  └─ PCI bridge: AMD/ATI [1002:1501]   ← Downstream bridge (internal routing)
       └─ Accelerator: AMD [1002:74a1]   ← MI300X GPU endpoint ("Aqua Vanjaram")

This adds +2 bridge hops between the BRCM downstream port and the actual GPU endpoint.

How They Combine to Break GDR

In a 4-NIC split-mask configuration, each NIC must serve 2 GPUs. One GPU is in the same switch partition (same root port), the other is in the other partition (different root port): 

GPU0 → NIC0: Both under root 00:01.1 (same partition)
  Path: GPU ← AMD_down ← AMD_up ← BRCM_down ← BRCM_up → BRCM_down → NIC_up → NIC
  Bridges: ~6 (borderline PHB, but within same hierarchy)

GPU1 → NIC0: GPU1 under root 20:01.1, NIC0 under root 00:01.1 (CROSS-PARTITION)
  Path: GPU ← AMD_down ← AMD_up ← BRCM_down ← BRCM_up_B →→ CPU →→ BRCM_up_A → BRCM_down → NIC
  Bridges: 8+ (PHB/SYS — crosses root port boundary)
  → RCCL: distance > 5 → GDR DISABLED

The MI300X's extra bridge hops make the within-partition distance already borderline (~6). The cross-partition case (GPU in one root port hierarchy, NIC in another) is where it truly breaks — RCCL sees the path going through the CPU root complex.

Why BF3-mini Didn't Have This Issue

The NVIDIA H20 GPU (tested with BF3-mini) presents as a direct PCIe endpoint — no internal PCIe bridge. In the H20 topology (from BD's XML): 

BRCM PEX890xx Upstream
  ├─ H20 GPU dev0     ← direct endpoint (no AMD bridge)
  ├─ Pollara NIC      ← sibling under same upstream
  └─ BRCM sub-switch → H20 GPU dev1

GPU and NIC are direct siblings under the same BRCM upstream port. PCIe distance = PXB (~4 hops) → GDR always enabled. The absence of the +2 AMD bridge hops keeps the distance well within threshold even for cross-partition cases.

Why AMD Internal Nodes Didn't Show the Issue

AMD's internal SMC300x test nodes use AMD CPUs (vs BD's Intel CPUs). The AMD CPU platform's memory subsystem delivered better CPU-RDMA path performance even in non-GDR mode, masking the performance impact. BD's Intel platform had:

  • Higher latency: 35% of reads >1.8µs (vs 3% internally)
  • Higher PTD_READS: constantly at 127 (vs <110 internally)
  • Lower line rate: capped at 330 Gbps (vs 390 Gbps internally)
  • Possible memory speed difference: BD's RAM running at 4400 MT/s vs internal 4800 MT/s

6. Solution & Fix

Fix 1: Linux Kernel Patch — Broadcom PCIe Switch Virtual Link Discovery

Kernel PCIe

Apply the Broadcom switch_discovery kernel module patches from LKML, with two modifications for BD's platform:

Patch Sources

  • https://lkml.org/lkml/2024/6/12/551 (Part 1)
  • https://lkml.org/lkml/2024/6/12/552/ (Part 2)

Required Modifications

Modification 1: Remove the SECURE_PART check (confirmed safe by Broadcom):

// REMOVE this check:
if (!SECURE_PART(cap_data1))
    return false;

Modification 2: For BD's PEX890XX specifically, also remove the P2PMASK / INTER_SWITCH_LINK check:

// REMOVE this check (BD's PEX890XX returns P2PMASK=0x300, VSEC_DATA=0x10460b0):
if (!(P2PMASK(vsec_data) & INTER_SWITCH_LINK))
    return false;

Post-Patch Steps

  1. Build kernel with the modified patch and load the switch_discovery module
  2. Trigger virtual-link discovery: 
    cat /sys/kernel/pci_switch_link/refresh_switch_toplogy
  3. Verify virtual links are visible: 
    tree /sys/kernel/pci_switch_link/virtual_switch_links

# Expected output (4 pairs for 4 physical switches × 2 virtual switches each):
/sys/kernel/pci_switch_link/virtual_switch_links
├── 0000:01:00.0
│   └── 0000:21:00.0 -> ../0000:21:00.0
├── 0000:21:00.0
│   └── 0000:01:00.0 -> ../0000:01:00.0
├── 0000:41:00.0
│   └── 0000:61:00.0 -> ../0000:61:00.0
... (8 entries total, 4 bidirectional pairs)

Fix 2: RCCL Patch — Handle Virtual Switch Links in Topology Models

RCCL GDR

A private RCCL branch by Wenkai Du adds new communication graph models that correctly handle the 4NIC/8NIC topology when PCIe virtual switch links are present.

Pull Request

  • ROCm/rocm-systems PR #3121 — "Add new models when virtual switch links are present" by wenkaidu

The RCCL diff was verified on top of commit 516ef1b (RCCL 2.27.7 HEAD). Without this RCCL fix, applying only the kernel patch causes the global (non-split-mask) AllReduce performance to drop from ~194 GB/s to ~90 GB/s because RCCL builds a suboptimal communication graph with the newly visible topology.

Both fixes must be applied together for correct behavior in all scenarios.
