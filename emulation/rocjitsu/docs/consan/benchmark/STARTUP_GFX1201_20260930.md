# ConSan startup profiling on gfx1201 — September 30, 2026

## Reproduction

The physical Radeon RX 9070 reproduces the high startup cost on revision
`5f4f7586c66`, including the earlier waitcheck optimization. The two workloads
use default mode, the default preset, fresh rocprofv3 exact-name allowlists,
strict static coverage auditing, CPU numerical oracles, and fresh native
references before and after each measurement. GPU work ran serially.

| Workload | September 26 startup | Current HEAD startup | No-op preparation fix startup | Before / after instrumentation |
| --- | ---: | ---: | ---: | ---: |
| PyTorch dense prefill, 30 selected kernels | 78.5 s | 85.046 s | 28.971 s | 84.227 / 28.210 s |
| PyTorch synthetic decode, 31 selected kernels | 90.1 s | 97.700 s | 32.905 s | 96.399 / 31.616 s |

Startup follows the benchmark runner's existing contract: instrumentation plus
the first synchronized operation, not total Python process lifetime. These are
single before/after campaigns, not distributions or benchmark thresholds. The
historical column gives scale; changes since September 26 prevent attributing
its difference from current HEAD specifically to the previous waitcheck patch.

Both before/after pairs retain identical allowlists and complete instrumentation:
996/996 selected sites for dense prefill and 867/867 for decode, each across
five applicable code objects. Both numerical oracles pass. Sampling, analysis
coverage, report capacity, and diagnostic limits were not reduced.

The same local Aorta checkout and ROCm Python stack as the September 26 campaign
were used: `/home/benoit/workspace/aorta`, `/home/benoit/gpu-venv-r102/bin/python`,
PyTorch `2.14.0+rocm10.2.0a20260918`, reported HIP `7.16.26373`. Artifacts record
package identities, source and hook hashes, commands, environment, and GPU identity.

Native second-run drift was +37.7% / +7.5% for the before prefill/decode campaigns
and +2.0% / -7.3% afterward. These runs do **not** establish precise steady-state
GPU overhead ratios. Native first-run drift was +1.1% / +2.1% before and
-6.7% / +0.2% after; the tens of seconds saved are visible directly in the hook's
host preparation timers, independently of millisecond device-run variation.

## Where the time goes

| Hook phase | Prefill before / after | Decode before / after |
| --- | ---: | ---: |
| Waitcheck | 1.445 / 1.401 s | 2.075 / 2.064 s |
| Inventory/preparation | 77.838 / 22.019 s | 89.319 / 24.891 s |
| Patch phase | 4.807 / 4.652 s | 4.907 / 4.562 s |

These sum per-object phase timers; the instrumentation clock also covers other
hook work. The inventory timer surrounds automatic preparation, which can
include a complete no-op transformation and register planning, not just decoding.
The previous waitcheck optimization does not address the dominant phase here.

A separate dense-prefill run was recorded with `perf record -F 99 -e cycles:u
--call-graph dwarf,8192`. The user temporarily changed
`kernel.perf_event_paranoid` from 4 to 0 to enable this. There were no lost samples.
The all-thread profile includes BLAS worker activity from the workload and its
CPU oracle; the main-thread report isolates ConSan's synchronous startup.
Main-thread inclusive sample shares include roughly 35% in CFG construction,
24% in indirect-branch discovery, 20% in resource-planning construction, and
15% in cross-call FLAT-pointer provenance relay. These overlap and must not be
added together; stack sampling is not a phase wall-clock measurement.

Four particularly expensive prefill objects take 23.114, 16.280, 11.600, and
10.766 seconds in preparation and ultimately need no instrumentation. They
contain 368, 336, 366, and 216 kernels, respectively, plus non-kernel helpers.
For example, only two of the 368 kernels are selected. This is not a missing
allowlist: selected kernels can legitimately need no LDS/synchronization probes.

The source explains both broad analysis and duplicated work:

- `consan_cfg.h::build_cfg_inputs_for_selection` deliberately keeps whole-object
  CFG inputs when non-kernel functions exist, to preserve shared-helper ownership.
- `relay_flat_pointer_provenance_across_calls` builds another whole-object CFG
  when functions exist, and can re-decode kernel bodies during propagation.
- `annotate_execution_owners` and `ResourcePlanningState` derive scopes for all
  kernel owners; resource planning also computes liveness and register summaries.
- `prepare_automatic_transform` first creates an inventory. When no runtime
  evidence binding is needed, it called `transform`, whose staged path created
  another inventory and then performed complete lowering, creating a third
  inventory and resource-planning state even for an empty observation plan.

## Implemented first fix

Automatic preparation now returns its already-complete no-op inventory when
Default mode has a valid empty probe plan, complete evidence requirements with
no binding needed, and an unchanged, well-formed result. Injected executors,
debug overrides, mutation requests, invalid or unsupported inventory results,
incomplete evidence requirements, and nonempty probe plans retain their existing
paths. Initial semantic analysis still runs; this
is not an early assumption that a selected kernel has no relevant accesses.

This removes the redundant second and third inventories and no-op resource
planning. It is architecture-independent pipeline code. Regression coverage
checks no-op plans on gfx942, gfx950, gfx1100, gfx1201, and gfx1250, plus a real
LDS access excluded by an exact production allowlist, against the complete
transform's observation and evidence products. Physical speedups were measured
only on gfx1201; no physical gfx950 speedup is claimed.

## Validation and post-fix profile

The full build and CTest suite pass: **12,094 passed, 89 skipped, one disabled,
zero failures** (121 seconds). The focused ConSan run passed 1,008 tests with two
opt-in benchmark skips. Modified C++ files pass clang-format and the diff passes
whitespace checks.

An initial full-suite invocation picked up the installed SDK's older
`librocjitsu.so` and failed only the C header smoke test because that library
lacked `rj_waitcheck_options_init`. The final full run used the build library
path from `cdna5-audit-20260925/env.sh`. The benchmark hook does not link against
that SDK library, so this test-environment correction does not affect the timing
comparison.

The post-fix dense-prefill perf replay also exits successfully, retains complete
996/996-site coverage, and loses no samples. Main-thread inclusive sample shares
still show CFG construction at about 32%, indirect-branch discovery at 21%, and
cross-call FLAT-pointer provenance relay at 15%. Resource-planning construction
falls from about 20% to 9% of main-thread samples. These relative, overlapping
shares identify remaining work; they are not independent elapsed-time savings.

## Next optimization targets

1. Keep a reusable decoded CFG and immutable instruction facts through inventory,
   binding, and resource planning instead of reconstructing equivalent graphs.
2. Bound helper analysis by selected roots and their call closure, while retaining
   all owners of any shared physical site that may be modified. Simply ignoring
   unselected owners can make register allocation or shared-helper patching unsafe.
3. Compute register-reference summaries once per immutable basic block, and
   aggregate them per owner. Context-sensitive liveness and return edges still
   need their existing correctness constraints.

The remaining 22–25 seconds in preparation are real overhead. The first fix
reduces duplication but does not solve whole-library analysis or remove the
need to profile gfx950 separately on hardware.
