1. The Key Architectural Difference

The fundamental difference is how each GPU presents itself on the PCIe bus:

Property NVIDIA H20 AMD MI300X / MI308
GPU PCIe Presentation Direct PCIe endpoint PCIe switch (1022:1500 upstream + 1002:1501 downstream)
Why? Monolithic die, single PCIe interface Multi-chiplet SoC — AID0's NBIO routes host PCIe to internal SDMA/HDP/NBIO across multiple dies
Extra bridge hops (Factor 1) 0 +2 (AMD upstream + downstream bridges)
BRCM switch host ports (Factor 2) Single or multi-host Multi-host: 2 upstream ports per switch → 2 OS root ports per physical switch
Same-partition GPU ↔ NIC distance ~4 hops (PXB) ~6 hops (borderline PHB)
Cross-partition GPU ↔ NIC distance Still PXB 8+ hops (PHB/SYS — crosses root port boundary)
GDR in split-mask mode Always enabled Disabled for cross-partition GPU/NIC pairs

The problem has two parts:
  1. The MI300X's internal PCIe bridge adds +2 hops within a partition (making intra-partition distance borderline at ~6).
  2. The PEX89104 multi-host partitioning splits the switch across two root ports — cross-partition GPU↔NIC paths go through the CPU root complex (PHB/SYS distance 8+).
Combined, RCCL sees distance > 5 and disables GPU Direct RDMA, falling back to slow CPU-mediated bounce buffers.

2b. Broadcom PEX89104 Multi-Host Partitioning

One Physical Switch, Two OS-Visible PCIe Hierarchies

Each physical PEX89104 switch is configured (via switch firmware / MFG EEPROM) with two upstream (host-facing) ports, each wired to a different CPU PCIe root port. This is not PCIe bifurcation — it is a Broadcom switch-level feature called multi-host mode.

Why Two Host Ports?

This is a platform design choice by the OEM (SuperMicro), not a BIOS setting. The reasons:

  • PCIe bandwidth: A single Gen5 x16 upstream = 64 GB/s. A GPU (x16) + NIC (x16) + NVMe (x4) would oversubscribe one upstream. Two x16 upstreams provide 128 GB/s total host bandwidth.
  • NUMA locality: Each upstream connects to a different CPU root port, which can be wired to different NUMA nodes for better memory locality.
  • Isolation: Each partition operates independently — one side can reset without affecting the other.

Can this be reconfigured to single-host mode?

Technically yes. The PEX89104 supports both modes:

Mode Description Configuration
Base Mode (single-host) One upstream port, all downstream ports under one PCIe hierarchy Traditional PCIe fan-out switch
Synthetic Mode (multi-host) Multiple upstream ports, embedded CPU allocates downstream ports to hosts Current MI300X platform configuration

However, this is not a BIOS setting or runtime toggle. The port-to-host mapping is defined in the switch's EEPROM / MFG firmware, programmed by the OEM using Broadcom's SDK tools (e.g., g4Xflash, MFG config tool). Changing it requires:

  • Broadcom SDK access (typically under NDA)
  • Reprogramming the switch EEPROM with a new topology definition
  • Full power cycle for changes to take effect
Why single-host mode is not the answer: Switching to single-host would consolidate all devices under one x16 upstream link, creating a bandwidth bottleneck (36 lanes of downstream demand on 16 lanes of upstream = 2.25:1 oversubscription). The kernel patch + RCCL fix is the correct solution — it preserves the multi-host bandwidth and NUMA benefits while making RCCL aware of the true physical topology.
The cross-partition problem: In split-mask mode with 4 NICs serving 8 GPUs, some GPUs must reach a NIC in the other partition. The path crosses root port boundaries: 
GPU0 → NIC0: Both under root 00:01.1 (same partition)    → ~6 hops (borderline)

GPU1 → NIC0: GPU1 under 20:01.1, NIC0 under 00:01.1     → 8+ hops (CROSS-PARTITION)
  Path: GPU ← AMD_bridge ← BRCM_up_B →→ CPU →→ BRCM_up_A → NIC
  RCCL: distance > 5 → GDR DISABLED

3. Why Does MI300X Have the Extra PCIe Bridge?

MI300X is a Multi-Die Package with Internal PCIe Fabric

The AMD MI300X is fundamentally different from a discrete GPU like the NVIDIA H20. It is a multi-chiplet package containing:

  • 8 XCDs (Accelerator Complex Dies) — the actual GPU compute units
  • 4 AIDs (Active Interposer Dies) — housing memory controllers, Infinity Fabric links, SDMA, HDP, and NBIO (North Bridge I/O) blocks. Only AID0 manages the primary host PCIe interface.
  • 128 GB HBM3 memory stacks (192 GB on some SKUs)
  • 7 bidirectional XGMI links at 128 GB/s each for inter-GPU communication

Why can't the MI300X connect directly as an endpoint?

Source: AMD Internal Confluence — MI300X PCIe Architecture Documentation

The AMD Instinct MI300X presents as a PCIe switch (identified by bridge device IDs 1022:1500 and 1002:1501) because it is a multi-chiplet SoC that uses an internal virtual PCIe hierarchy to manage its complex I/O subsystem.

1. Internal Chiplet Management

The MI300X is comprised of multiple dies, including Active Interposer Dies (AID) and Accelerated Compute Core Dies (XCD). While the GPU contains multiple functional blocks, only AID0 manages the primary host interface. The internal "switch" allows the system to route traffic between the external host PCIe bus and the various internal blocks (SDMA, HDP, and NBIO) across these chiplets.

2. Virtual PCIe Topology

In a discrete GPU (dGPU) like the MI300X, the "switch" exists within the GPU package itself. While the Root Complex is on the motherboard, the GPU presents a virtual link where the upstream port and switch downstream port represent internal connectivity to the final GPU endpoint.

3. Discovery and Enumeration

Diagnostic tools and drivers rely on this bridge chain to discover the GPU. The full PCIe device chain is: 

PCI bridge:              AMD     [1022:1500]   ← Top-level upstream bridge (NBIO)
  └─ PCI bridge:         AMD/ATI [1002:1501]   ← Downstream bridge (internal routing)
       └─ Accelerator:   AMD     [1002:74a1]   ← MI300X GPU endpoint ("Aqua Vanjaram")

4. Address Space & Virtualization

The internal PCIe bridge provides address decode, BAR management, and routing for multiple internal functions (GPU compute, SDMA engines, HDP) exposed as separate PCI functions. It also provides IOMMU integration and ACS (Access Control Services) required for SR-IOV and GPU virtualization (MxGPU).

In short: The NVIDIA H20 is a discrete GPU with a single PCIe endpoint interface. The AMD MI300X is a multi-chiplet SoC where AID0's NBIO block must present as a PCIe switch (1022:1500 → 1002:1501) to route host PCIe traffic to internal blocks (SDMA, HDP, NBIO) across multiple chiplet dies. This is an inherent architectural property of the multi-die design — not something that can be bypassed.

5. Bridge-Hop Counting: Why Distance Matters

NCCL/RCCL PCIe Distance Classification

NCCL counts the number of PCIe bridge hops between two devices to classify their proximity. This determines whether GPU Direct RDMA (GDR) is enabled:

Classification Distance Meaning GDR
LOC 0 Same device Enabled
PIX 1-3 Same PCIe switch complex Enabled
PXB 4-5 Different PCIe bridges, same switch Enabled (threshold)
PHB 6-8 Across PCIe host bridge DISABLED (distance > 5)
SYS 9+ Across NUMA / CPU socket DISABLED

7. How the Fix Works

Without kernel patch: OS sees two unrelated PCIe trees

OS view — no connection between partitions:

Root 00:01.1 → BRCM_upstream_A → GPU0 + NIC0    (same-partition: ~6 hops)
Root 20:01.1 → BRCM_upstream_B → NIC1 + GPU1    (same-partition: ~6 hops)

Cross-partition path (GPU1 → NIC0):
  RCCL sees: different root ports → PHB/SYS distance 8+ → GDR DISABLED

With kernel patch + RCCL fix: Virtual links bridge the partitions

Kernel module "switch_discovery" reads Broadcom VSEC registers and exposes:

  /sys/kernel/pci_switch_link/virtual_switch_links/
    0000:01:00.0 ──── 0000:21:00.0    (upstream A ↔ upstream B: same physical switch!)
    0000:41:00.0 ──── 0000:61:00.0    (next switch pair)
    ...                                (4 bidirectional pairs for 4 physical switches)

RCCL's new topology model (PR #3121) sees:
  "GPU1 (under 21:00.0) and NIC0 (under 01:00.0) are on the same physical switch"
  → Treats cross-partition paths as same-switch → enables GDR

Result:
  GPU 0 → NET/ROCM-IB/0/GDRDMA    (same-partition NIC)
  GPU 1 → NET/ROCM-IB/0/GDRDMA    (cross-partition, now recognized as same switch)
  GPU 2 → NET/ROCM-IB/1/GDRDMA
  ...all 8 GPUs use GDR
Important: The kernel patch alone is not enough. Without the RCCL fix (PR #3121), the newly visible virtual links cause RCCL to build a suboptimal communication graph, dropping global AllReduce from ~194 GB/s to ~90 GB/s. Both patches must be applied together.
